# 全データ整合性移行の検討案

2026-10-11。親 [change record](README.md) は Proposed。これは設計検討であり、本番実行・リセット・未知の履歴統合の承認ではない。

## 対象の意味

全データを棚卸しして整合性を確認する。ただし、全IDの再生成や全レコードの書き換えは行わない。正常なID、利用者の入力、履歴、時刻、金額、結果を保持し、証明できた旧→正規IDと参照閉包だけを変換する。「最新の名前からIDを再計算したら違った」だけでは移行対象としない。

確認範囲は、ドメインの原本と投影、収集運用DB、保存アーティファクト、外部配送、設定・機械学習生成物まで。ソースモデルの一覧と実DBの一覧を照合し、未知のテーブル・列・イベント・JSON形状・ファイルがある場合は未分類として計画を止める。ソースから想定した一覧だけを全件確認と呼ばない。

## 推奨方式：停止中の整合したコピーを変換し、検証後に一括切替

稼働DBへ小さな修正を順番に加える方式より、整合した原本を保存し、そのコピー上で変換・検証する方式を第一候補にする。イベントDBと収集DBの間に共通トランザクションがないため、切替中は全writerを停止し、検証済みの組を揃えてから起動する。実際のファイル数、切替方法、容量・所要時間は本番構成の確認後に確定する。

コピー方式でも複数ファイルの置換は一つのDBトランザクションにはならない。永続的な切替記録と起動前検査によって、途中停止で新旧混在のまま起動させない。単なるファイルrenameの連続をatomicと呼ばない。

### 1. 読み取り診断と全件分類

- 本番DBのschema/version、テーブル・列・index・FK、行数、イベント種類とversion、snapshot、JSON構造、ファイル/外部保存先を取得する。秘密情報・全DB内容を公開画面やログへ出力しない。
- 最初の登録情報、現在の名称、外部識別子、過去の変換・修復記録、レース参照、全生成経路を照合する。
- 各レコードを `Keep`（正常・不変）、`Migrate`（対象と参照）、`Conflict`（衝突）、`Unverifiable`（証拠不足）、`UnknownShape`（未対応形式）へ分類する。分類結果の合計は全件数と一致させる。
- 同名、同じ正規化結果、旧方式で生成されたIDは同一実体の十分条件ではない。証明できないものを推測で統合しない。
- 本番対象の原本読取ができない間は、移行設計の条件を整理できても、完全移行可能とは判定しない。現在のサイトでは初回登録情報を読めない。

### 2. 移行manifestと参照閉包

manifestは entity種別、旧ID、新ID、根拠、source/event version、対象DB・schema・入力hash、変換レシピversion、参照位置、件数、判断を持つ。変換前提と一致しない入力には適用しない。承認対象のmanifestを固定し、preview後のデータ変化で対象が拡大しないようにする。

主キー/外部キーだけでなく、イベントdata/metadata、snapshot、JSON、複合キー、派生ID、収集metadata、外部メッセージを参照閉包に含める。型と意味を理解した変換を使い、DB全体の文字列置換はしない。過去のURL・エラー文・診断アーティファクトは歴史的証拠として保持し、稼働参照と区別する。

### 3. イベントとID衝突

- 一対一の旧stream→空の正規streamへの移行を第一候補とし、event ID、sequence、時刻、domain値、関係の意味を保持する。AggregateId、data、metadataのどれを変更する必要があるかをserializer/versionごとに定義する。
- 移行先streamが既に存在する場合、同一sequenceの衝突があり得る。イベントを連結したり、番号を振り直したり、片方を削除したりしない。完全同一性を含む具体的な統合規則とhydrate/replay検証を承認するまで `Conflict` とする。
- snapshotはイベントと独立に正当性を確認する。無条件削除や「再生すれば必ず戻る」を前提にしない。既存snapshotの正確な変換、または実証されたrebuildのいずれかをレシピに固定する。
- 投影は実際に再構築できるものだけreplayを候補とする。利用者の予想・メモ・元の入力など、再取得で復元できないデータを失わない。
- 既存repairのoperation/fingerprint、source snapshot hash、sidecarとbackup manifestの照合も変換契約に含める。履歴JSONを再serializationして参照を変えた際に既存fingerprintが無効になる可能性がある。無条件にhashを書き直して監査の意味を変えず、原本の監査証拠と移行後の整合性証拠を区別し、具体的な検証手順を固定する。
- HorseIdからRaceEntryIdなどが派生する場合、そのIDと結果・オッズ・予想票等の全参照を合わせて変換する。馬IDだけ更新して完了としない。

### 4. 収集運用と配送の整合性

対象resourceのidentity、resource key参照、state、request/task、attempt、lease、outbox、reservation、repair issue、failure/selection、artifact/locatorを個別に分類する。過去の試行と失敗は証拠として保持する。旧タスクを書き換えるか、歴史的に保持して正規対象へRecoveryを作るかは、それぞれの型と現行契約に基づいて固定し、先に動かす側で意味を変えない。

SQS/Lambda等の外部配送はDB停止だけでは凍結されない。producer、dispatcher、consumer、outbox、inflight、再配信を確認する。migration前の配送が新DBへ遅れて書き込むことを防ぐdrain/fenceが必要。無条件purgeや「停止したので配送なし」という推測は使わない。

resourceの新旧衝突やactive taskの重複も未解決のまま切替しない。旧履歴を保存しつつ、移行後に正規対象の処理を一度だけ進める。

### 5. コピー上の実行と検証

1. 定期・手動・外部からのwriterを停止、配送をdrain/fenceし、停止を観測する。
2. WAL等を含む整合した全保存先のバックアップを作る。原本は不変で保存し、schema/件数/hash/時点を記録。復元テストを実行する。
3. offlineコピーへ固定manifestを適用する。型ごとの純粋な変換ロジックと、SQL/ファイルIO・実行状態管理を分け、単体テスト可能にする。
4. DBのintegrity/FK/unique、全件分類、参照閉包、旧稼働ID残存、event hydration/replay、snapshot/投影一致を確認する。
5. 不変データは行ごとの値比較・hash等で保持を検証する。行数一致だけでは保存内容の正しさを証明しない。変更データも承認された位置以外が変化していないことを比較する。
6. 本番と同じバイナリ/設定境界で、移行後のコピーに対し実handler/APIの読み書き・再起動を確認する。外部配送や本番への通信は隔離する。
7. 未分類・未解決衝突・参照漏れ・復元不能があれば、切替せず原本を保持する。これを「移行成功」と報告しない。

### 6. 切替・復旧・ロールバック

切替記録は入力generation、出力generation、検証hash、各保存先の切替状態を保持する。停止後の保存先一致検査を起動の必須gateとする。全保存先が検証済みgenerationであることを確認してから、正規ルールのアプリを起動し、限定的な対象ジョブから再開する。

最初の実行成功、元エラーの非再発、後続dispatchと終端結果、予想・履歴・プロフィールの読取を確認する。原因未確認の別エラーは独立に扱う。

新環境への書込が始まる前は、検証済み原本の組へ戻す。再開後は新たな利用者入力や成功結果があるため、古いバックアップへの無条件復元は禁止する。差分保存・再適用またはforward修正の計画を先に定める。単なる旧binaryへのrollbackもDBschema互換性を確認する。

移行mappingは実行と監査のartifactに閉じ込め、定常resolverの恒久的な別名/redirect増加で完了を代替しない。ただし、既存redirect削除は全参照とcallerの移行完了を証明してから別の明示的stepで行う。

## 方式の比較

| 方式 | 評価 |
| --- | --- |
| 稼働DBへ逐次SQL置換 | 全参照・複数DB・外部配送の混在と部分失敗が大きい。第一候補にしない。 |
| 整合コピーの型付き変換＋停止切替 | 原本保持、差分検証、切替前の試行が可能。容量/停止時間/切替gateの実証を条件に推奨。 |
| 全データの再取得・投影だけ再生成 | ユーザー入力や履歴の再構築が保証されない。全データ保存の代替にはしない。 |
| 恒久runtime redirect/例外分岐 | 既存機構はあり得るが、今回の単一ルールへの移行完了とはしない。 |
| DBリセット | 本案に含めない。対象と影響を特定した別承認が必要。 |

## 必要な反例・受け入れ証拠

- 同名別source、sourceなし、旧入力不明、複数候補、既存正規stream、異なるDBgeneration、未知event/JSON、不正JSONを誤変換しない。
- 派生IDと全参照を閉じ、利用者入力・結果・順序・時刻を保持する。
- preview無書込、同じmanifestの再実行、copy変換途中、保存先ごとの切替途中、起動途中、遅延配送、再開後rollbackを検証する。
- runtime producer/import/manual/API/collector/predictorのID契約を照合し、移行済みデータから同じミスマッチを再生成しない。
- 本番保存先の実一覧とschema/データを照合するまでは、全件移行/復旧の受け入れを閉じない。

## 未確定事項

本番の完全schema/データ、元のsource根拠、既存targetstream、serializer保証、全保存先容量、配送drain/fenceの実経路、切替と起動gate、再開後差分保全は未確定。M2のsource inventoryとT2のtarget evidenceを照合後、T3でexact recipe、変更file、test、外部契約・実行権限を固定する。新診断API/UI/workflowが必要な場合は有限routeと認証・返却項目をREADMEに明記してレビューする。本案から勝手に新しい公開口を追加しない。

本番の読取経路の候補として、既存GitHub配備workflowはSSH host/user/keyをGitHub secretsから供給している（`.github/workflows/app-deploy.yml:168-190`）。ローカルAWSログイン不能とは別経路であり、秘密鍵の取出しは不要。専用の限定read-only診断をこの経路で実施できるか検討する。ただし通常の配備workflowを診断目的でそのまま起動してはいけない。診断command、実行対象、返却項目、出力保護、timeout/負荷、承認とworkflow変更が必要なら別の具体的gateを先に定義する。現在は調査候補のみで、変更・dispatchはしていない。
