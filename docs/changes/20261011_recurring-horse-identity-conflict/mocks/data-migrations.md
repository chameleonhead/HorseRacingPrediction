# 管理画面の移行操作案

AC5。設計のみ・実装未開始。デスクトップ1280pxと狭幅390pxを想定。既存Settingsの運用カテゴリから独立Pageへ遷移する案。複雑な移行全体をDialogへ押し込まない。

## 初期状態

```text
その他設定 / データ移行
データ移行
保存済みデータを確認し、検証した計画だけを実行します。

移行の種類 [ 登録済みデータの識別子整合性移行 v1 ▾ ]
対象環境   本番（読み取り専用表示）
対象保存先 サーバー設定から取得（利用者のパス入力なし）

[診断・プレビューを作成]

実行履歴
対象・処理段階・結果・開始日時・最終更新       [詳細]
```

移行種類はサーバーのallowlistだけ。SQL、shell、ファイルパスや任意commandの入力欄は作らない。

```text

確認済み保存先 … / …

解消が必要な項目と根拠を確認してください。

分類 [要確認 ▾]   対象検索 [                ]
対象     現在のID → 移行先     判定・根拠         [詳細]
…（サーバー側pagination）…

[診断をやり直す]  [移行を実行：無効、理由を表示]
```

最初から全件をブラウザーへ返さない。件数はサーバーで集計し、行はpage取得。識別情報・判定・次の行動を優先する。技術ID/serializer/hashは詳細へ置き、危険性は色だけで示さない。

## 実行可能状態・確認

対象とプレビューfingerprintは読み取り専用で表示する。保存先が変わる、previewが古い、backup未検証、writer未停止、外部配送未drain/fenceならサーバーが実行を拒否する。UIのbutton無効だけを安全gateにしない。

```text
この計画では、保持 …件・変換 …件、未解決0件です。
停止・バックアップ・変換・検証・切替が必要です。
原本の保存場所/検証状態 …  （秘密情報は表示しない）

[移行を実行] → 最終確認Dialog
  対象環境、移行計画、変更件数、停止影響、復旧境界を表示
  [戻る] [この計画で実行]
```

確認後も二重送信・多tab・通信再送を同じoperationとして扱う。遷移先はoperation固有の詳細Page。画面を閉じても実行継続し、同じURLへ再訪して状況を取得できることが必要。

## 実行中・障害・完了

```text
移行実行の詳細                         実行状態: 検証中
対象 本番 / 計画 … / 実行者 …
開始 …   最終更新 …   現在の段階 検証   対象件数 … / …

段階       状態       終了時刻/問題
停止確認   完了       …
backup     完了       …
変換       完了       …
検証       実行中     …
切替       未開始

[最新状況を確認]
接続が切れています。実行を再送せず、この操作の状況を再取得してください。
```

進捗はdurable journalから取得し、timerだけで架空のpercentを出さない。切替時にAPIが止まる場合は、予定された再接続待ちと原因不明の失敗を区別する。成功はrunnerの最終検証が保存された場合だけ。HTTP受付成功を移行成功と表示しない。

失敗は段階、変更/未変更、原本保持、復旧可能状態、次の行動を示す。切替後の未確認状態は「復旧確認が必要」とし、無条件な再実行/restore buttonを出さない。DBリセットは提供しない。

## 状態・操作の受け入れ

- loading：既存結果を消さず操作をdisable、keyboard/focus/labelを維持。
- empty：移行種類なし、候補なし、検索0件を区別し、次の行動を示す。
- error：通信失敗で入力/operationIdを失わず再取得できる。技術例外をそのまま表示しない。
- narrow：概要と操作は縦積み、表は優先列+詳細。対象・判定・主要操作は消さない。
- component tests：状態、blocked reason、validation、二重送信、権限、再接続を観測可能な結果で確認。
- browser：Settingsからの発見、preview→確認→operation詳細、再訪、focus/keyboard、狭幅・長いID・大量pageを確認。実装後に行う検証であり、モックをテスト完了としない。
