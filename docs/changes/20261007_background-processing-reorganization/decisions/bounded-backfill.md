# Bounded typed batch recovery (D1)

Proposed 2026-10-08; RC3/RC4/RC7/RC8. This design adds control metadata and preserves existing business rows. It does not claim that actual production legacy rows were inventoried or migrated.

## Evidence and preserved contracts

CollectionPlatformStore.cs:3729 expands Backfill by date, skipping an existing race-discovery state before RequestAsync. At :3784 PeriodRecollection uses the same BackfillBatchEntity/table; RequestCoreAsync :281–303 reuses the same batch's task even if terminal, while a different batch reruns terminal days. ResumeIncompleteBackfillBatchesAsync :3906 currently reads every incomplete batch and invokes the Backfill branch unconditionally. Both public creation endpoints accept caller-supplied IDs. Prefixes therefore do not prove workflow kind. BackfillBatchEntity has no kind or cursor. Existing API test `BackfillRecovery_ExpandsAllHolesBeyondTypicalPageSize` uses 101 days directly through the store, whereas public creation ranges are month/31-day bounded.

Preserve synchronous HTTP completion and receipts for both public creation endpoints, their existing range limits, same-ID replay counts and normal per-day commit semantics. Background recovery alone is bounded per cycle. Fix type collisions explicitly: a batch ID cannot be used for a different kind/provider/range. A typed mismatch or an existing unclassifiable batch returns 409 with a safe code, never retags existing work.

## Additive persistence

Use two new CollectionPlatform tables, not new fields in collected race/horse/profile data and not rewriting old batch rows:

- `collection_batch_recovery_progress`: BatchId primary key/reference, Kind (Backfill/PeriodRecollection/Unknown), NextDate nullable, LastVisitedSequence, ReviewReason nullable, LastErrorCode nullable. Error codes are allowlisted and cleared after a successful chunk; retry uses the next normal cycle, with no separate persisted retry timer. Kind/range derives from the typed creation operation for new batches; old batches start without a sidecar. Index known runnable kinds + LastVisitedSequence + BatchId. Unknown has no runnable date and cannot complete the batch.
- `collection_batch_recovery_scan`: one row holding legacy discovery keyset position and a monotonically increasing visit sequence. Cursor updates occur in the same writer transaction as the associated metadata/normal requests. Reset discovery position at end to catch newly inserted legacy rows. No timer-tick or network-derived state is persisted.

Migration creates empty tables/indexes only. It neither resets existing ExpansionCompletedAt nor creates tasks/requests, changes states, retries failures or infers identity. New batch row plus typed sidecar are inserted in one immediate transaction. For existing known sidecars, creation must check exact kind/provider/range. Two concurrent different-kind creation requests cannot both win. An existing completed untyped row remains historical data; reads do not change it.

## Legacy discovery and classification

Each five-minute cycle visits at most 10 incomplete legacy rows missing metadata, ordered by BatchId with a durable keyset cursor. The bound is rows returned, not a claim that every underlying SQL scan is O(1). Use scalar/distinct queries on linked root request evidence and verify supporting indexes with EXPLAIN; add an index only if the plan needs it. Source evidence must agree on reason, provider, date range, resource/definition and workflow. Child Discovery requests cannot alone identify the parent workflow. A BatchId string or absence of requests is never positive evidence.

If all relevant evidence uniquely establishes Backfill or PeriodRecollection, insert a sidecar starting at From (safe replay), never infer previously completed dates from counts. If evidence is absent, mixed or inconsistent, insert Unknown + an allowlisted ReviewReason and leave all business rows/requests/completion markers untouched. Advance discovery cursor past Unknown so it cannot block later batches. Unknown does not reclassify or retry automatically every cycle. An operator investigation can produce a separate, previewed and explicitly authorized resolution; no new classification-write endpoint is introduced here.

Read surfaces show `処理種別を確認してください` for Unknown/mixed rows. Do not present a guessed kind or mark them complete. Finite-progress acceptance applies to safely typed runnable batches; unknown batches have explicit blocked visibility and are never silently discarded. Live rollout must inventory the Unknown count and approve its treatment before enabling recovery; local tests cannot prove production coverage.

## Bounded recovery and concurrency

At most five typed batches and at most seven dates per batch are processed in one periodic cycle, with the existing five-minute post-cycle delay. Between chunks observe pause/cancellation and the cooperative time budget. Select least LastVisitedSequence, then BatchId; after each attempted committed chunk move it to the tail using the global sequence. This creates durable round-robin progress across restart. Large batches cannot monopolize every cycle.

For each periodic chunk, acquire the existing gate once and an IMMEDIATE SQLite writer transaction. Recheck batch identity and sidecar position, load at most seven relevant existing date-state rows, execute each kind's normal logic through private RequestCoreAsync, update NextDate/LastVisitedSequence and commit together. Never call public RequestAsync while holding its gate. No outbound network is performed inside this transaction. A second process waits for the writer transaction and then rereads the updated cursor; selection/writes/checkpoint share the transaction, so no separate long-lived recovery lease is necessary. Transaction rollback leaves that entire chunk uncommitted. CompletionAt is set only after the last date's normal operation is durable; it is a normal workflow transition, not a migration rewrite.

Backfill skips existing state exactly as today. PeriodRecollection must still call its request/deduplication path for every date, even if a terminal state exists. Do not substitute Backfill's state-exists check. An operation failing before commit leaves NextDate unchanged. When DB access recovers, a separate short fenced metadata transaction records LastErrorCode and advances the visit order only if NextDate/LastVisitedSequence still match the failed attempt; otherwise a concurrent successful attempt wins. This prevents one poisoned batch from starving others without fabricating date completion. If even that transaction cannot run, report the DB failure and exit/back off rather than spin. Retry at the next normal period, preserve the global unknown-failure stop policy.

Manual synchronous creation/replay keeps per-day transactions and visits the full requested range. Accumulate CreatedTask/reused results exactly as before, including same-ID complete replay. A manual date only advances the sidecar if it is the current contiguous NextDate; replay never moves progress backwards or falsely skips an earlier gap. Each day shares the type check and transaction helper. Periodic chunks and manual dates serialize through DB writer transactions; injected interleaving tests must show no duplicate work or cursor regression.

## Read and recovery surfaces

Add an optional Recovery metadata property to BackfillBatchSnapshot and its DTO: Kind, RecoveryState (Unclassified/Ready/NeedsReview/Completed), NextDate and safe ReviewReason. Missing metadata is displayed as unclassified; reading never performs classification writes. Preserve original historical task counts, holes and links; annotating mixed history is not authorization to filter away old records. DTO addition is backwards-compatible for clients that ignore unknown fields; default-null behavior must be tested with old responses.

`RecoverBackfillHolesEndpoint` submits each actual hole.Resource/Definition as CollectionReason.Recovery under a new recovery batch; it does not infer date expansion kind. Keep that resource-bound manual operation for both workflow types, with its current guards/receipts. It must not classify the original batch or create a `backfill:` resource merely because a `recollection:` hole is recovered. The earlier worker suggestion to reject all PeriodRecollection holes is not adopted: route naming alone is insufficient reason to change this valid existing manual operation. Unknown auto-expansion remains blocked independently.

## Required proof and rollout

Old-schema fixture migration preserves every pre-existing row/value/key/link; both new tables begin empty. Exercise empty, populated, legacy101-day, zero-request, mixed-reason, custom-ID collision, interrupted PeriodRecollection, already-completed and paused/held cases. Crash before/after each periodic commit; interleave two independent store instances and manual replay; confirm fair progress after restart, exact receipt counts, no cursor regression, no false completion and unchanged failure history. Extend CollectionPlatformStoreTests and CollectionOperationsEndpointTests rather than validating only metadata objects.

Before any separately authorized target upgrade: inventory source schema/batch evidence, take and test consistent backup, pause/drain using existing procedure, apply additive migration, reconcile old business data exactly, preview classification, inspect Unknown rows, then explicitly decide enable/resume. Old executables can ignore sidecars but contain the unsafe legacy recovery path; rollback must set BackgroundSchedulersEnabled=false and keep pipeline paused until a compatible recovery version is deployed. Never drop sidecars or restore over newer collected data as an implicit rollback. No production operation is authorized by this design document.

Implementation scope: CollectionPlatformStore batch paths (prefer one focused partial for new recovery helper), CollectionEntities/DbContext/SchemaMigrator, operations recovery service, existing creation/read endpoints and mapper/DTO model, relevant API/Collector migration/store tests. All Store writes serialize with hold refactoring. I4 independently verifies actual SQLite and transport paths; Lead owns migration acceptance and cannot declare live migration complete from fixtures.
