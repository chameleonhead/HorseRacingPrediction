# Runtime status contract (D3)

Proposed 2026-10-08. RC6/RC8. Existing source evidence: Jobs.razor already displays per-lane LastStartedAt/LastCompletedAt from persisted task progress; CollectionOperations.razor has an authorized `/jobs/operations?tab=monitoring` page, a 30-second refresh, and reusable FluentDataGrid/UiState components. The existing dashboard GET loads progress, up to 10,000 notifications and all backfills; it must not be called more frequently merely to observe loop liveness.

## State ownership and bounded storage

Add a singleton in-memory runtime-status recorder in the API. It owns exactly eight logical action slots: dispatcher, discovery planner, refresh planner, task-lease recovery, backfill recovery, dead-letter reconciliation, alerts and metric delivery. The two planners share their producer HostedService but retain independent status. Metric delivery is channel driven: waiting without a message is healthy and has no periodic stale threshold. This is instance-local diagnostic state, never capacity/hold/deduplication authority and never a DB heartbeat. No existing stored values or schema change.

Each slot holds a coherent immutable snapshot under a short local lock: action key; enabled flag; effective interval or null for event-driven; State (NotObserved/Running/Waiting/Error/Disabled); Reason (Paused/NoDueWork/CapacityFull/RepairHeld/BudgetExhausted/Error or null); LastStartedAtUtc, LastCompletedAtUtc, LastSuccessfulCycleAtUtc, LastProgressAtUtc; LastDurationMilliseconds; current-cycle inspected/created/reclaimed/sent/completed counts; ConsecutiveErrors. InstanceId is a random startup identifier, not hostname or credential; InstanceStartedAtUtc and GeneratedAtUtc are response-level fields. Counts describe the latest completed cycle; incomplete current-cycle counts are separate or omitted, not silently mixed.

Begin/complete/fail are scoped to a cycle token, so late callbacks cannot overwrite a newer cycle. Host shutdown cancellation is not a business failure. All timestamps are UTC; elapsed/budgets use TimeProvider monotonic timestamps. A successful empty cycle updates successful-cycle time but never progress time. Progress means actual durable business action or successfully accepted delivery; inspected/skipped rows and UI refresh are not progress. Emit counters only after the corresponding commit/accepted operation; ambiguous SQS delivery follows existing ambiguity semantics and does not fabricate success.

No state survives restart; null means not yet observed on this instance. The UI displays that explicitly instead of reconstructing historic loop activity from task timestamps. Existing per-lane job history remains independently visible. Unknown/disabled are distinct. A periodic action missing its expected completion for `3 × effective interval + producer cooperative budget` gets a stale indicator derived from age; this is not proof of an outage or permission to retry. Event-driven delivery shows pending activity/error and last delivery, not stale merely for idle time.

## Additive HTTP surface

New GET `/api/v2/admin/collection/operations/runtime-status` returns `{ runtime: { instanceId, instanceStartedAtUtc, generatedAtUtc, actions: [...] } }` with a fixed-size action list. No query parameters or write operation. All fields above are explicit DTO fields; nullable timestamps/interval are serialized consistently. DTO enums use the existing Contracts serialization conventions, verified by contract tests rather than assumed. It reads recorder memory only, returns Cache-Control: no-store and honors cancellation. Use existing API-key protection; missing/invalid key returns the existing unauthorized behavior and no status data. Do not add anonymous-path exemptions.

Wire through Contracts request/response DTOs, the existing typed ApiClient transport/facade interfaces and AdminApiClient, matching existing route registration and response wrapper conventions. UI has the existing `[Authorize]` boundary. Error responses retain existing client error handling; a 404 from an older API is shown as status unavailable, not a dead service. Existing clients ignoring this new route remain unchanged; no field is removed or reinterpreted in existing dashboard/progress responses.

## User flow

Reuse the monitoring tab and header actions. Above existing lane metrics show a section titled `バックグラウンド処理の稼働状況` with `このAPIインスタンスの記録` and last refresh time. Fixed eight rows use FluentDataGrid with action label, state/reason, last successful cycle and last progress. Expandable read-only details hold start/end/duration/counters and instance start; no per-row retry/resume controls. Japanese labels describe purpose, not class names. Status text and icon accompany color.

Runtime section loads independently so dashboard failure does not conceal a successful runtime response, and runtime failure does not remove task data. Keep last good runtime values with `更新できません・表示は以前の情報です` on failure. One in-flight runtime request at a time. Reuse the existing 30-second page tick; request runtime status on initial load, manual refresh and monitoring-tab ticks. No second timer, no busy retries, cancel requests on disposal, no extra dashboard refresh frequency. Switching away from monitoring stops periodic runtime requests.

Desktop and 390px narrow wireframe is in ../mocks/runtime-status.md. Narrow view retains action/state and the two important timestamps using stacked details or approved responsive grid layout; keyboard-accessible details, explicit labels and normal Fluent focus styling. No sorting/filtering/pagination for eight fixed roles. Main use case: open `/jobs`, choose `収集運用` (one navigation), see which action is active or waiting and when it last advanced, without opening a dialog or needing internal IDs. Existing `/jobs` lane times continue to answer whether actual jobs ran.

## Evidence required before acceptance

The existing backfill tab also displays D1's optional Recovery kind/state/NextDate and safe review reason. Missing metadata reads `未分類`; Unknown reads `処理種別を確認してください`, never success. Preserve counts, holes and the existing resource-bound hole-recovery action. No new classification/resume control is added. A cycle that classifies a legacy batch successfully may be healthy while that batch needs review: show the batch warning separately, not a fictitious job completion or service crash. Add old-response/null-metadata, mixed legacy and ready/completed component cases.

Recorder tests: fake-clock empty/success/failure/paused/budget/disabled cycles, restart-null, monotonic elapsed and late-token rejection; no database writes. Endpoint tests through actual HTTP + AdminApiClient/typed facade: exact wrapper and fixed membership, unauthorized/valid key, missing older route, cancellation. bUnit: loading, retained stale data, safe errors, long labels, unknown after restart, and separate lane progress vs loop success. Real browser: 1280px/390px, keyboard details/manual refresh, monitoring-tab cancellation and no overlapping requests. No live credentials in artifacts. CI build/format and related regression precede final Ubuntu full-suite verification.

Exact implementation files proposed: new API CollectionController/CollectionRuntimeStatusRecorder.cs, new Endpoints/Collection/GetCollectionRuntimeStatusEndpoint.cs, route-registration owner, new Contracts/Collection runtime DTO/response files, existing ApiClient Collection interfaces/facade, Web/ApiBrowsing/AdminApiClient.CollectionPlatform.cs, Web/Components/Pages/CollectionOperations.razor and css. Instrument each existing/reorganized action in its exclusive worker slice; UI worker owns only Contracts/client/UI integration after recorder shape is frozen.
