# Bounded live-resource hold snapshot (D2)

Approved with the parent implementation design on 2026-10-08, RC4/RC5/RC8. 'Bounded' here means bounded application pages/materialization and live-only scope; SQL work may examine a large held live prefix. It is not a hard per-call latency guarantee. Scheduler's independent 500-candidate/time budget remains unchanged.

## Frozen pre-implementation source evidence and decision

HeldTaskIdsAsync in CollectionPlatformStore.RaceRepairHolds.cs currently materializes Resources then matching historical Tasks. Recurring GetPendingDispatchesAsync, ReserveDispatchesWithinCapacityAsync and AcquireNextExecutionAsync use that snapshot; reservation/acquire additionally check identities afresh. RaceRepairHoldTests prove mutable mapping is significant. Existing telemetry demonstrates a SQLite identity UDF, but resolving EventStore identity inside a collection reader and evicting a 512-entry cache cannot prove stable precheck results for duplicate resources. Do not copy that UDF directly into a writer path.

Choose a connection-local temporary `HeldResourceSnapshot(ResourcePk PRIMARY KEY, IsHeld NOT NULL)` per operation. Capture active hold IDs once. If no holds, use ordinary predicates and skip snapshot work entirely. For each required live source, stage its exact distinct, not-yet-classified keys once in a connection-local `HeldResourceWorklist(ResourcePk PRIMARY KEY)` using the provider-generated parameterized command. Enumerate those keys and resources in pages of at most128, fully materialize/close each reader, resolve MatchesHold once for each not-yet-snapshotted resource, then insert classified values into Snapshot. Pure SQL joins subsequently use this stable pre-mutation answer. Worklist keys are never exposed as hold decisions; finish populating a predicate's relevant resource set before aggregating it. This preserves duplicate-resource consistency without a growing C# cache or persistent canonical-ID state.

TEMP storage grows with distinct relevant live resources, not task/history size; C# materialization stays at bounded pages plus bounded selected results. The transaction owns one open physical connection. Reserve/acquire retain their existing immediate writer transaction; pending-candidate reads use a deferred read transaction, never acquire a writer transaction merely to search. Establish cleanup ownership before creating either TEMP table, including failure between creates. Finally commit/rollback, drop both TEMP tables with an independent cleanup token before returning the connection to its pool. If cleanup fails, discard/clear that connection from pooling and surface diagnostics; never reuse a contaminated TEMP snapshot. The actual-provider command/parameter/rollback probe passed; integrated lifecycle and performance verification remain required.

## Query responsibilities

Implementation refinement after RC5 profiling: an initial inner-keyset/DISTINCT/Take128 rewrite reduced p50 from538ms to319ms but retained repeated candidate COUNT/sort work and remained slower than the204ms baseline. The selected internal refinement stages the exact live keys once per source in Worklist, then performs indexed bounded reads. Every source remains server-side, including bounded selected-key inputs; no per-key IQueryable.Contains execution is allowed. EF CreateDbCommand preserves bindings rather than parsing SQL debug text. This preserves snapshot semantics and original eligibility predicates; no unresolved snapshot state or persistent data change is introduced. Revised measurements and actual partial-create/cancel/pool cleanup passed; Lead accepted RC4/RC5 locally on2026-10-10 (see rc5-evidence.md). The rejected global-resource-driven EXISTS alternative could scale with unrelated history and is not used.

1. **Pending candidates:** preserve all existing dispatch eligibility: undelivered, unreserved/expired reservation, Ready, current generation, task/outbox due, aggregation-window exceptions and one open current-generation outbox. For each lane preserve Priority DESC, AvailableAt ASC, OutboxId ASC and the existing candidate cap. Filter using the snapshot before the limit; continue bounded read pages through held rows. Merge lanes with the current allocator/order. No persisted scan cursor and no reuse of the dispatch fairness tie-break cursor as a scan cursor.
2. **Capacity:** count active unexpired StartPending/Running execution leases first; full capacity exits immediately. Then populate only resources for exact legacy in-flight rows, count distinct surviving EnvelopeIds, and stop if capacity is full; then exact reserved-live rows, then selected resources/eligible lanes as needed. Preserve all old per-category predicates and overlap exclusions. Mixed envelope counts once if any unheld eligible sibling survives; held-only is zero. Active execution leases always count separately. Exact final reservation, not runtime metrics, is authority.
3. **Lane existence:** SQL DISTINCT lane/EXISTS uses the same eligibility and snapshot; no full task list in C#. Keep existing Realtime/Normal/Background allocation and persisted fairness state.
4. **Selected reservation/acquire:** preserve exact count, envelope, same-lane, generation, expiry/token and consistency guards. Snapshot says not-held AND fresh MatchesHold says not-held immediately before mutation. Fresh validation bypasses TEMP and resolver cache. Mapping unheld→held rejects; held→unheld within this operation remains conservatively excluded by the earlier snapshot. Never silently shrink an inconsistent mixed envelope into a valid smaller one.
5. **Repair/history operations:** explicit single-race hold creation, snapshot, release and historical alias inventory retain their existing semantics. They are classified exceptional control/history paths and are not silently narrowed to active-only. Ordinary single-resource IsRepairHeldAsync callers keep their invariant boundaries; share a captured hold-ID list only within the same appropriate transaction, not identity results across stages.

Canonical identity, ambiguous/unknown/conflicting aliases, malformed data, synthetic discovery/backfill/recollection exclusions and fail-closed behavior remain exactly MatchesHold's semantics. Direct valid race-GUID resolution can avoid opening EventStore, but no weaker normalization or inference is added.

## Tradeoffs and falsifiers

TEMP adds page reads and temporary writes/joins. Writer-lock time still includes live-resource identity resolution; history×10 with fixed live work must not scale materialized history or resolver inputs. This is not a promise that live-backlog×10 costs the same. Measure row/resolver counts and lock duration; reject unexplained >10% repeatable regression under RC5 rather than remove holds or silently add a durable cache. If live-held-prefix costs remain unacceptable, return to design for durable paging; do not introduce a hard early-stop that starves later eligible work.

Actual EF/SQLite integration must prove: immediate and deferred transaction TEMP support; page-reader disposal before resolver access; distinct-envelope counts after joins; held-prefix refill and stable ordering; duplicate resource resolved once for the precheck; both identity flip directions; cancellation/failure cleanup and pooled connection reuse with no leaked TEMP objects. Then run existing RaceRepairHoldTests, CollectionDispatchStarvationReproductionTests and telemetry/capacity regressions. A provider-only scratch proof establishes mechanism feasibility, not production path or performance acceptance.

No main-DB schema change or business-data migration is needed for this component. Its TEMP table is never migration state, never persisted canonical truth and never carried between calls. Source scope: CollectionPlatformStore.RaceRepairHolds.cs, affected dispatch/capacity/acquire partials in CollectionPlatformStore, DomainRaceResourceIdentityResolver and corresponding Collector/API tests; serialized ownership with D1 implementation. Lead independently reviews final SQL predicates and existing invariants before accepting I4 evidence.
