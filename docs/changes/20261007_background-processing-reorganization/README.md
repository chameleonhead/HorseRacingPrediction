## Recommended architecture and stage-one decisions

Business responsibilities are delivery, periodic work production, independent lease recovery and backfill. Alerts, dead-letter reconciliation and metric buffering remain support services. Revision: combine schedule/planning only; retain Watchdog independently, so maximum API HostedServices goes from eight to seven, not six. Removing more service objects is not a performance objective. No new scheduling framework, event bus, canonical-ID cache or concurrency increase in stage one.

1. **Fast delivery, fixed 1 second:** recover execution leases, observe pause, cheaply check definitely-full capacity, then fetch bounded eligible candidates, select with existing lane allocator, atomically reserve, send SQS wake. DB/outbox remains truth; wake loss has periodic fallback. At capacity-full cycles skip candidate/identity work, but never treat a metric snapshot as reservation authority.
2. **Periodic producer coordinator:** discovery registration and due-refresh registration only, each with its own next-due time and error boundary. Preserve 1-minute cadence. Check host cancellation and a 30-second cooperative producer slice budget between atomic requests; inspect at most 500 candidates per cycle. Advance a keyset cursor past inspected candidates, including held/ineligible ones, rather than always starting at row1. Exceptions before a decision do not falsely advance past uncommitted work; action failure backs off to its next period. Budget limits cooperation, not blocked SQLite I/O.
3. **Independent Watchdog:** sole owner of task-lease recovery; remove its duplicate invocation from the producer. If background schedulers are enabled, recover every minute even if the old Watchdog flag is false (preserve scheduler recovery responsibility). Otherwise recover at the configured Watchdog cadence if enabled; if both are disabled, do not silently enable recovery. It remains independently scheduled while a producer is blocked. Under healthy DB conditions the first recovery check starts within one configured period of expiry, plus measured action duration; shared DB lock contention can still delay recovery and must be visible, not claimed as a hard deadline. Execution-envelope recovery stays in the 1-second dispatcher. Both recovery paths can run while paused without resuming/dispatching work.
4. **Backfill recovery, separate 5 minutes:** bound the existing all-batch/date pass in mandatory stage two. Keep separate even after bounding unless a subsequent measured design justifies integration. Stored ranges/count cannot be assumed month-limited.

No CPU reduction percentage is promised. The intent is fewer needless reads/writes and one owner per lease category, not fewer service objects for its own sake.

### Due-registration rules and atomic boundary

Current candidate limit precedes skipping HasActiveTask; 500 active due rows can hide eligible row501. Current permanent failure sets Failed without necessarily clearing NextCollectionAt, and ScheduledRefresh is not protected by ordinary same-revision registration deduplication. These are source-backed possible unnecessary work, not proven causes of the current production CPU value.

Stage one filters Failed and exact resource/definition active tasks in SQL **before** order/Take500. Preserve due-time ordering, profile refresh interval, valid extraction revisions and explicit manual/recovery requests. Add scheduler-only TryScheduleDueAsync: acquire the collection gate once, begin a SQLite writer transaction, reload state and recheck due/Failed/active conditions, call private RequestCoreAsync, save and commit. Do not call public RequestAsync while holding the gate. Two independent contexts/store instances must prove the atomic guard; an in-process lock alone is not enough. A failure between candidate read and registration must not recreate the failed task.

### Dispatch and safe low-risk query changes

- Capacity hint reads only indexed unexpired StartPending/Running execution leases. If that lower bound already reaches maximum capacity, return without heavy candidate work. Otherwise proceed normally; legacy/reserved capacity still belongs to final atomic reservation. An uncertain hint must not falsely declare available capacity.
- Before expiration cleanup opens a writer transaction, an indexed existence check can skip the transaction when no execution lease is expired. It is a hint only: the actual cleanup rechecks under the existing transaction; a race may defer cleanup until the next tick, not bypass fencing.
- Read active repair-hold IDs once within each reservation/acquire collection transaction and reuse that list. Keep both snapshot-held membership and fresh identity validation; EventStore identities can change despite a collection writer lock. The explicit single-race hold path is separate.
- For a valid direct race-GUID resource ID, DomainRaceResourceIdentityResolver can validate ID/metadata without opening EventStore. Create its context only for date/course/number aliases; preserve ambiguous/unknown/conflicting-ID rejection exactly.
- Do not add indexes speculatively: NextCollectionAt, execution lease status/expiry and RaceDate/RaceNumber indexes already exist. New proposals require representative EXPLAIN QUERY PLAN and actual-row/query-count evidence.

### Progress and fairness rules

Use stable `(NextCollectionAt, ResourcePk, DefinitionId)` ordering with a fixed due-time horizon for each sweep. Cursor advances after an inspected candidate's atomic decision (created, already active, held or policy-ineligible), including skips. At page end continue next minute; at exhaustion reset horizon/cursor for the next sweep. Do not use OFFSET over a changing queue. Atomic current-state recheck overrides stale page data. If a row moves behind the cursor or becomes due during the sweep, reconsider it on the next sweep; cursor position is not success state. Startup may reset an in-memory periodic cursor because persisted requests/state enforce deduplication; this may repeat inspections, not work. Cursor reuse across changed eligibility/config requires reset.

Test with 1,001 stable candidates (first 500 held/ineligible), a shortened budget interrupting a page, same due timestamps, deleted/retimed rows, concurrent task creation and hold release. Under continuous uptime, a finite stable set with completing DB operations is revisited by one full sweep; with row budget alone this is ceil(N/500) cycles, while time-budget slices require counting actual inspected rows. Do not promise bounded waiting under endless earlier arrivals, endlessly blocked DB operations or endless restarts. Record sweep age and progress; a stable overdue backlog with no progress for three producer periods triggers an actionable stalled status and investigation, not blind retry. D1 must specify durable backfill rotation rather than assume this periodic in-memory cursor suffices.
