## Purpose and boundary

This proposal describes an authenticated administrator experience for a bounded, read-only inventory and evidence preview over the application's configured local SQLite stores. It is an acquisition aid for the parent all-data migration design, not an approved transformation, fixed apply manifest, production census, or recovery operation. The parent record remains the authority for identity rules, complete target inventory, apply, writer fencing, cutover, rollback, and resume decisions.

The preview must reconcile every one of the 47 source-mapped application tables in the four known SQLite stores against the physical objects actually observed. Every table receives a declared row-evidence role in [reference-scope.md](reference-scope.md). `SchemaOnly`, `Unsupported`, `UnknownShape`, `Unavailable`, and `NotInspected` are outcomes, never zero rows or silent omission. Source mappings do not prove deployed schema or record counts. External queues/DLQ, files, backups, model storage, and host state remain explicitly outside this local-store command unless a separately approved acquisition is added.

All reads are bounded, keyset-paged, non-pooled, read-only and query-only. A separate durable operational journal records command acceptance, progress, interruption, and result summaries; it must not be placed in or modify the four inspected source stores. Source observations occur at different times and are non-atomic. Even a complete page walk is not a fixed migration manifest and cannot prove that records did not change between pages.

The preview never changes source data or makes Keep/Migrate/apply decisions. It does not infer identity from names, display calculated candidate IDs, guess missing provenance, merge streams, reset data, retry jobs, resume a migration, or expose raw payloads, URLs, metadata, paths, SQL, credentials, caller identity, or free-form exceptions.

## Proposed bounded operation

Use the existing API binary in a fixed preview-command mode selected before `WebApplication.CreateBuilder` and all normal host/service startup. Proposed invocation is `dotnet HorseRacingPrediction.Api.dll --run-data-migration-preview <operation-guid>`; server code fixes executable/assembly path and uses `ProcessStartInfo.ArgumentList` for exactly the fixed mode plus a server-generated canonical GUID (never shell concatenation). The mode rejects any other argument or configuration override, loads the existing configured store locations, and does not build the web host, resolve migration-owning store constructors, run schema migrators, register collection definitions, or dispatch background work. The authenticated API durably reserves an `Accepted` operation and starts only this fixed child. The command runs with the same service identity and permissions already assigned to the API; it receives no Docker socket, additional privileges or elevation, new credential, or broadened filesystem authority. This is a proposal, not proof that production process-spawn policy permits the child; verify behavior on Windows and Linux before deployment.

The command enumerates a finite allowlist of configured surfaces, reconciles all 47 mapped application tables and known metadata objects, and uses bounded keyset scans with batched typed evidence extraction. Each source-store connection is independent and read-only. Row shapes not covered by a typed reader become explicit incomplete/unknown evidence; they are not skipped. Exact typed rows, supported reference roles, and non-row limitations are enumerated in [reference-scope.md](reference-scope.md).

Compose already mounts the API's writable application state at `/data`, where configured local databases, backups, and DataProtection keys live. Proposed journal path is `/data/migration-preview-journal/operations.db` in production (the fixed `migration-preview-journal/operations.db` child beneath configured `CollectionPlatform:StateDirectory` elsewhere); it is outside the four source database files and uses the existing service identity/volume. Require a service-only directory/file ACL (Unix `0700`/`0600`; Windows ACL granting only the existing service identity), and fail closed on permission, symlink/reparse-point, or path-collision checks. No new host mount, privilege, or credential is proposed. The journal does not exist today; deployed identity, ACL behavior, and child launch/termination remain verification gates. It persists sanitized operation state and typed, allowlisted observation records required by Items, not raw source rows, event/metadata JSON, source URLs, SQL, paths, actors, keys, or free-form exceptions. Proposed limits: 30-day TTL for terminal operations, 128 MiB per operation, 1 GiB total journal bytes, with reserved terminal-status space. At budget/retention limits, stop scanning and persist `Incomplete/JournalBudgetReached`; never evict active work or claim completion. Cleanup is bounded and journal-only.

Each command has a 30-minute wall-clock limit, 10,000,000 aggregate row cap, per-query timeout of 1 second, 128-key page, 64 KiB maximum text payload checked in SQL before materialization, JSON depth 16, 16 typed references per row, and a 1 MiB API page limit. The separate memory budget and measurement method are specified below. Exceeding any limit becomes explicit `Truncated`/`Incomplete` evidence and stops the relevant scope. Admission is globally single-flight across API/child restarts, not a process-local semaphore: an atomic journal reservation binds a canonical RequestId to one operation, and the child must acquire an exclusive OS file lock in the journal directory and validate that reservation before opening any source store. It holds that lock through the read phase. Same RequestId returns the same durable operation. A different RequestId while a reservation or lock is active returns 429 immediately, with no wait or second scan. After API restart, a lock still held means `StatusUnknown/Busy`; a nonterminal record whose lock is released may be marked `Interrupted` only after journal reservation/ownership revalidation, then a new explicitly requested operation may start. Never infer ownership from PID or elapsed time, never kill a process based on journal contents, and never auto-resume. API cancellation may terminate only its own retained process handle/tree, then must observe lock release before marking terminal. Windows and Linux tests must cover duplicate start, API restart with child alive, child kill/lock release, and failure to acquire lock before any source read. On restart the UI shows `Interrupted`/`StatusUnknown`; an admin must explicitly start a fresh preview, which revalidates policy and source schema.

The journal state machine is `Accepted → Running → Completed | Incomplete | FailedSafe | Interrupted`. API receipt carries operation GUID and status URI. Status contains only fixed safe reason codes, phase/store/table progress, separate UTC observation times, bounded counters, and `IsNonAtomic`. `Completed` means the declared supported pages ended; it is not migration-ready or target-complete. Terminal records expire after 30 days. Per-operation/global storage budgets and cursor behavior are specified below.

Items pages read only journaled observations and never re-read live source files. Protected cursors bind operation, registered table code, last typed key, policy version, persisted surface/schema fingerprint, and a fixed 30-minute expiry; invalid, expired, mismatched, or over-4-KiB cursors return 400 before journal/source IO. Do not log cursors, RequestIds, operation IDs, or source keys. The journal budget includes database, WAL, SHM, and temporary journal files; reserve terminal-status bytes before each scan batch. Cleanup removes expired terminal journal records only, never source files.

Memory limits are a budget, not a hard RSS guarantee: keep one 128-key page and bounded 64 KiB source buffers live, set the child .NET GC heap hard limit to 256 MiB, and sample RSS at page checkpoints. RSS above 512 MiB stops the operation as `Incomplete/MemoryBudgetReached`. Tests measure peak memory; no OS-enforced RSS ceiling is claimed. Isolated fixture tests require identical schema/row snapshots before and after. For live stores, prove query-only/read-only access and absence of writes by this command while labeling concurrent-writer changes possible; do not claim byte-for-byte live-file identity.

## Proposed admin screen

Add one dedicated authorized Settings page at `/settings/data-migration-preview` and an operation detail/revisit route `/settings/data-migration-preview/{operationId:guid}` using the same component. An accepted receipt navigates to the detail route; the catalogue supplies the latest retained operation reference when returning through Settings. Mount/revisit may read catalogue/journal status once but never starts a scan. The page offers `Start preview`, `Refresh status`, and explicit `Next page` only, and disables Start while an operation is active. It displays operation phase, UTC observation timestamps per store, bounded object/table reconciliation, typed identity/reference summaries, truncation/unknown/unavailable states, and the non-atomic warning. It never shows raw rows or source metadata and has no Apply, Execute, Resume, Reset, or job Retry control. Browser close does not own the operation lifetime; reopening reads the journal. Desktop and 390px layouts retain table/surface, state, and next action; keyboard focus, duplicate start, loading, empty, interruption, stale, and restart states are specified in [mock](mocks/preview.md).
