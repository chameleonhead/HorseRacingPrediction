The read plan must not treat `Horses` as the only root source: that would miss orphan Horse IDs in the other five allowlisted tables and overstate coverage. Use six independent source phases (or a bounded SQL `UNION` of their distinct keys) with a separate binary keyset continuation and at most 128 distinct keys per page for each source. The six physical mappings are `Horses`, `EventEntity` (Horse aggregate IDs and sequence-1 registration evidence), `JraSubjectProfileReadModel`, `HorseRaceHistories`, `HorseWeightHistories`, and CollectionPlatform `collection_resources` filtered to the exact Horse resource type/provider. Emit source/phase-level observations; the same Horse may therefore appear in several phases without collapsing its evidence. An ID present in a reference source but absent from `Horses` is an explicit missing-root/unverifiable observation, not silently omitted. Noncanonical raw IDs are counted/statused only and never echoed.

Each source phase is bounded by its own ordered keyset (`key > lastKey`, binary ordering, server limit 128); within that page, read all relevant registration-sequence-1 events and associated reference rows in batched parameterized queries. Do not use OFFSET, call `GetHorseIdentityDiagnosticAsync` once per row, materialize all IDs into memory, or turn this into N+1 lookups. EventEntity handling must retain duplicate sequence-1 and unknown/malformed event type/shape as explicit `Conflict`/`UnknownShape` evidence rather than filtering them into “missing.” Reference row limits and over-fetch for duplicate/truncation detection are server constants. Never return raw event/metadata/URL or unknown identifier text. Truncation is visible per source phase. Independent source phases and stores are observed at different times; no shared snapshot or fixed apply manifest is implied.

## Proposed bounded acquisition contract

1. Start with one GET and advance with the same GET plus one opaque cursor query. No body, user-supplied path, SQL, table name, or horse-ID scan instruction.
2. Cursor is server-protected, at most 4 KiB, and expires within 30 minutes. It binds a policy version, server-selected configured surfaces/schema assumptions, and keyset position. It has no durable report/journal. Invalid/expired/restart tokens require a fresh scan; the UI does not promise resume.
3. Inspect physical schema using allowlisted source definitions; return recognized surface codes and coverage/count status rather than raw SQL/path/connection data. Unknown tables/columns/versions are Unknown/Unsupported, never silently omitted.
4. Read rows only from the fixed six-table allowlist: EventStore `Horses`, `EventEntity` rows for Horse aggregates (parse the supported registration event; count unknown/malformed event types or shapes as `UnknownShape`), `JraSubjectProfileReadModel`, `HorseRaceHistories`, and `HorseWeightHistories`; CollectionPlatform `collection_resources` (exact horse resource type/provider only). Use batches of at most 128 root identities and batched typed references. Do not call the single-horse endpoint N times or load the database into memory. Other known application tables are SchemaOnly/NotInspected, not row-counted. PredictionSchedule, optional LocalCollectionQueue, migration metadata, sidecars, external queues/files/model storage are also NotInspected for rows.
5. Use only approved wire evidence: canonical HorseId, current/initial names, optional birth date, validated canonical JRA identity/status, bounded related RaceId/HorseNumber, coverage/truncation, counters, and per-store observation time where available. Do not return calculated candidate IDs, raw URL/event/metadata, path, actor/caller log, raw malformed identifiers, or exception text.
6. One preflight-service singleton immediate admission slot shared by all preflight requests, no wait queue; busy returns 429. It does not replace or broaden the existing single-horse diagnostic slot or affect other operations. Per-request upper bound 30 seconds, cancellation, query-only connection and deferred read transaction. No polling loop. Payload-size, JSON-depth, response-size, and driver timeout limits are server-owned and no looser than the existing single-horse diagnostic limits.
7. Each response and the page retains the non-atomic warning. Pages may span separate read times; a scan count reconciliation is not a stable snapshot and cannot create a fixed apply manifest. Coverage of unsupported/external/not-configured sources is explicit.
