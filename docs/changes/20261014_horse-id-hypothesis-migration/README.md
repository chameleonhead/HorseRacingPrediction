## Goals and non-goals

- Preview exact manifest consequences, then stage an immutable operation request and expose durable status/results independently of browser or API lifetime.
- In an offline, one-shot mode of the existing API image, physically change only typed, source-defined HorseId references for the accepted manifest across configured stores. Preserve event sequence, event type, payload semantics, and unrelated data.
- Reject before the first source write on invalid/duplicate manifest entries, ambiguous roots, an existing canonical target stream, unknown affected schema or event shape, unsupported references, count/identity invariant failure, or an incomplete source-store set.
- Keep failures paused and inspectable. Resume is a separate, explicit operational decision after verification; no automatic retry, reset, alias, or unpause.

Out of scope: name-based identity inference; merging or resequencing streams; changing identity guards; deleting/recreating databases; rewriting unknown JSON/string fields; migrating every noncanonical horse by discovery; automatic workflow dispatch from the web request; and claiming the 47 source-mapped tables are a target-data census. The deployed preflight inventories configured source surfaces but does not prove a coherent point-in-time generation.

## Evidence and migration rules

The existing `DeterministicIdGenerator.BuildHorseId` creates a source-derived Horse ID when given a recognized JRA identity; otherwise it can create a name-derived ID. `BuildRaceEntryId` incorporates both race and horse IDs. `EntryRegistered` stores HorseId/HorseNumber but no creation-time source identity. Existing repair apply code writes redirect/suppression state rather than physically rewriting the event stream (`src/HorseRacingPrediction.Api/Endpoints/Repairs/ApplyHorseIdentityRepairEndpoint.cs`; `src/HorseRacingPrediction.Application/Repairs/SubjectIdentificationRepairService.cs`). Therefore a redirect is not completion of this migration, and a display-name match cannot recover the original identity input.

The operator manifest is the sole authority for old-to-new root selection. For each pair, preview must show source evidence and its limitations, old and derived IDs, root/target presence, and typed dependent-reference counts. A mapping remains a hypothesis until explicitly accepted. Same-name/different-source is a required counterexample. Multiple old roots for one destination, any pre-existing destination stream, duplicate or unknown event shape, or a reference that cannot be typed and transformed blocks the whole operation before writes; no automatic stream merge or partial “best effort” apply.

The migration inventory must reconcile all configured physical stores and sidecars against the source-defined schema at runtime. The 47 known table mappings guide typed coverage but do not assert target presence or absence. Every discovered HorseId-bearing location must be classified as transformed, verified unchanged, or unsupported; an affected unknown location blocks. Apply must not scan-and-rewrite arbitrary text, URLs, metadata, or opaque event JSON. Typed reference transformations must preserve non-identity fields and verify before/after counts, referential closure, and stable race-entry IDs recomputed from their existing RaceId and transformed HorseId. Any snapshot/cache/projection either has a proven typed rebuild/invalidation path or blocks apply; no stale projection is declared correct by assumption.

## Proposed operator flow and routes

The authenticated admin UI shows the three known candidates as unchecked hypotheses. The operator reviews evidence, explicitly selects exact old-ID/JRA-identity pairs, requests a read-only preview, then stages that exact preview. A stage receipt is `AwaitingActions`, not `Running`: a separate operator/agent action must dispatch the existing GitHub Actions deployment workflow with the opaque operation GUID. This handoff is a deliberate safety boundary; the API does not invoke GitHub, accept arbitrary shell input, or claim the operation started. On workflow claim, the existing deployment safety sequence pauses/drains and stops the API before the fixed offline CLI runs.

| Method and route | Purpose | Result / failure behavior |
| --- | --- | --- |
| `POST /api/v2/admin/horse-id-migration-previews` | Validate bounded manifest and read-only consequences | Preview ID, exact normalized manifest, evidence and blockers; invalid input `400`, unavailable/incomplete evidence is non-executable |
| `POST /api/v2/admin/horse-id-migration-operations` | Stage the exact preview and reserve durable operation state | Opaque operation GUID and `AwaitingActions`; stale preview or conflicting reservation rejected; no source writes |
| `GET /api/v2/admin/horse-id-migration-operations/{operationId}` | Read journal status and bounded result pages | Status survives browser/API restart; invalid ID `404`; this route never scans source stores or starts work |

All routes use existing server-side admin API-key authorization and typed contracts. No key, raw source URL/JSON, database path, arbitrary destination ID, command text, or free-form exception is returned or logged. Operation IDs are opaque, and logs use safe result codes only. Existing actual repair/migration routes are unchanged; the earlier six generic data-migration routes remain unimplemented, not prerequisites. Preview is no-write and bounded to 16 pairs, pages of 128 rows, JSON payloads of 64 KiB and depth 16, with finite row/byte/time budgets frozen before execution; an exceeded budget blocks apply. Stage binds an immutable normalized manifest and policy/schema/root fingerprint, rejects stale previews and concurrent reservations, and records explicit hypothesis and non-recovery confirmations. Missing identity provenance alone does not block an explicitly accepted hypothesis; contradictory positive evidence does.

## Execution, durability, and recovery

The existing deployment workflow remains the only production runner. The workflow accepts an operation GUID, verifies it is a staged operation, pauses the pipeline, drains active producers, stops the API, and runs existing WAL/backup checks before invoking the fixed CLI mode in the same API image. The CLI starts before web hosting, store migration/bootstrap, queue consumers, or background workers. It reads only server-configured store paths and the immutable staged manifest, acquires a single-operation lock, validates the reservation and full write preconditions, and writes bounded typed pages with durable progress in a separate operational journal. It accepts no caller-provided path, SQL, shell, or destination ID. No new credential, socket, privilege, or local AWS login is required.

The journal is outside the stores being migrated, protected by existing application-state directory permissions, and contains only the approved manifest, safe typed status/reason codes, bounded counts/checkpoints, and sanitized typed result items. It stores no raw event payload, source URL, metadata, database path, secret, or free exception. It has a finite capacity and retention policy; if capacity is reached, processing stops safely and records `Incomplete`, never discarding evidence or claiming success. Journal reservation, workflow claim, CLI ownership, and terminal status are idempotent by operation GUID. A second runner is rejected while ownership is held. Process/API restart or child termination produces a durable interrupted/partial state; it is not auto-resumed. Recovery requires revalidation against the recorded operation and a new explicit workflow action. Source-store transactions are not cross-database atomic, so partial writes remain a real risk; the workflow must restore a coherent backup set or leave the service stopped and collection paused rather than resume from an unverified mix.

Implementation must reconcile backup coverage for every configured database and required sidecar before production apply. Existing deployment backup steps and repair backups cover named subsets, not automatically the complete migration set. Preserve backup/WAL checks; this proposal does not waive them. Proven restoration of every generation is not an approval prerequisite under the user's accepted non-recovery risk; test restore with representative fixtures and attempt coherent production backup without claiming it guarantees recovery. A persistent partial/unverified migration marker interlocks domain/collection writes and global resume, including after API restart; missing/corrupt journal state fails closed while authenticated status reads remain available. Fence stale affected leases/outbox tokens and test delayed external delivery; do not purge external queues or add runtime aliases. After CLI success, restart the API still paused and verify SQLite integrity, event replay/sequence, typed references across stores, canonical roots, projections/snapshots, and clean health. Only then explicitly recover selected eligible failed tasks and resume general collection; unpause alone does not reset failed tasks. Verify successful replacement work and continued lane progress, preserving unrelated stop reasons.
