## Execution, durability, and recovery

The existing deployment workflow remains the only production runner. The workflow accepts an operation GUID, verifies it is a staged operation, pauses the pipeline, drains active producers, stops the API, and runs existing WAL/backup checks before invoking the fixed CLI mode in the same API image. The CLI starts before web hosting, store migration/bootstrap, queue consumers, or background workers. It reads only server-configured store paths and the immutable staged manifest, acquires a single-operation lock, validates the reservation and full write preconditions, and writes bounded typed pages with durable progress in a separate operational journal. It accepts no caller-provided path, SQL, shell, or destination ID. No new credential, socket, privilege, or local AWS login is required.

The journal is outside the stores being migrated, protected by existing application-state directory permissions, and contains only the approved manifest, safe typed status/reason codes, bounded counts/checkpoints, and sanitized typed result items. It stores no raw event payload, source URL, metadata, database path, secret, or free exception. It has a finite capacity and retention policy; if capacity is reached, processing stops safely and records `Incomplete`, never discarding evidence or claiming success. Journal reservation, workflow claim, CLI ownership, and terminal status are idempotent by operation GUID. A second runner is rejected while ownership is held. Process/API restart or child termination produces a durable interrupted/partial state; it is not auto-resumed. Recovery requires revalidation against the recorded operation and a new explicit workflow action. Source-store transactions are not cross-database atomic, so partial writes remain a real risk; the workflow must restore a coherent backup set or leave the service stopped and collection paused rather than resume from an unverified mix.

Implementation must reconcile backup coverage for every configured database and required sidecar before production apply. Existing deployment backup steps and repair backups cover named subsets, not automatically the complete migration set. Preserve backup/WAL checks; this proposal does not waive them. Proven restoration of every generation is not an approval prerequisite under the user's accepted non-recovery risk; test restore with representative fixtures and attempt coherent production backup without claiming it guarantees recovery. A persistent partial/unverified migration marker interlocks domain/collection writes and global resume, including after API restart; missing/corrupt journal state fails closed while authenticated status reads remain available. Fence stale affected leases/outbox tokens and test delayed external delivery; do not purge external queues or add runtime aliases. After CLI success, restart the API still paused and verify SQLite integrity, event replay/sequence, typed references across stores, canonical roots, projections/snapshots, and clean health. Only then explicitly recover selected eligible failed tasks and resume general collection; unpause alone does not reset failed tasks.
