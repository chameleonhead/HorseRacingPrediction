# T6 — typed migration readiness

Status: source-only plan; implementation is not released by this note. The accepted manifest contains three operator hypotheses, not verified historical provenance. This plan does not authorize a production read, migration, restart, retry, or resume.

## Purpose and source findings

Provide a bounded physical rewrite for only the explicit old-Horse-ID → canonical-JRA-identity manifest, after a complete pre-write inventory of the configured stores. Never infer a mapping from a display name, alter unknown JSON/text, merge streams, resequence events, or treat the source-mapped 47 tables as a production census. The existing inventory is [persistence-inventory.md](../20261011_recurring-horse-identity-conflict/persistence-inventory.md); it enumerates 20 EventStore, 25 CollectionPlatform, 1 PredictionSchedule, and 1 optional LocalCollectionQueue application tables, but target schema/rows and optional-store presence must be discovered at runtime.

Relevant source facts:

- `EventStoreDbContext` registers EventFlow events/snapshots and persists selected read-model properties through `System.Text.Json` converters (`src/HorseRacingPrediction.Infrastructure/Persistence/EventStoreDbContext.cs`). `EventEntity` aggregate IDs/sequences and snapshot keys are identity-bearing; existing migrations impose uniqueness. Preserve event IDs, type/version metadata, timestamps, sequence numbers, and all non-ID payload values.
- `EntryRegistered` has `EntryId`, `HorseId`, `HorseNumber`, and `PreviousHorseId`, but no creation-time JRA identity (`src/HorseRacingPrediction.Domain/Races/EntryRegistered.cs`). `EntryCollectedDataUpdated`, `EntryResultDeclared`, and `RaceResultDeclared` have additional typed Horse-ID fields. `RaceEntryAssignmentsRepaired` contains previous/current typed entry lists and a fingerprint (`src/HorseRacingPrediction.Domain/Races/RaceEntryAssignmentsRepaired.cs`). Transform only these registered types through their actual versioned serializer; unknown type/version/shape blocks before writes.
- Read-model JSON contains typed references: race context entries, result/comparison entries and winners, jockey histories, memo subject snapshots. Horse profiles and histories are keyed by `HorseId`; identity repair candidate/redirect and subject-repair rows contain explicit source/target IDs. Their non-ID evidence remains unchanged. The mapped property declarations and JSON conversions are in `EventStoreDbContext.cs` and the corresponding `Application/Queries/ReadModels` types.
- Collection `ResourcePk` is distinct from external `ResourceId`; preserve external JRA IDs/URLs and task/request/attempt/lease/outbox GUIDs unless a versioned field is proven to be an internal Horse ID. `requestedByHorseId` is an example of an explicitly named metadata key; arbitrary metadata strings are not identity references. Collection mappings are in `CollectionPlatformDbContext.cs`, entities in `CollectionEntities.cs`, and schema bootstrap/migrations in `CollectionPlatformSchemaMigrator.cs`.
- `CollectionPlatformStore` constructors/schema migrators and `PredictionScheduleStore` initialize storage. The offline engine must use the configured paths with direct, explicitly controlled SQLite connections; it must not resolve those store constructors, start web/hosted services, or run schema migration as a side effect.
- `.race-locks` repair barriers and backup manifests are validated against repair events, fingerprints, projections, snapshots, and file hashes by `RaceWriteCoordinator.cs`. Do not blindly re-hash or rewrite them. A referenced repaired race blocks until an exact recipe updates the typed repair event and its validated sidecar consistently; historical backup packages remain immutable.
- Existing HTTP writes use `RaceWriteEndpointFilter` and its `identity-resolution` key, and `RaceWriteCoordinator` can lock arbitrary keys. That protects only cooperating HTTP callers; it does not establish a fence for every background, queue, scheduler, schema, or external writer. The concrete missing lease path is the JRA profile lane: `JraSubjectProfileCollectionHandler` calls `JraSubjectProfileApiClient.SaveAsync`; the sole typed-client registration in `src/HorseRacingPrediction.Collector/Program.cs` has API-key, timing, and retry handlers, but not the already-registered `CollectionWorkerLeaseHandler`. The same Collector host is used for Lambda and local-queue entry modes. The profile PUT `/api/v2/admin/subjects/{kind}/{subjectId}/profile` publishes `CollectHorseProfileCommand` and then `UpdateHorseProfileCommand`, and installs only `RaceWriteEndpointFilter`, not `RaceActiveCollectionEndpointFilter` (`PutSubjectProfileEndpoint.cs`). The latter validates a race resource and is not the profile-route lease check. A newly deployed worker can carry the existing task/token headers and the profile route can validate them before either command; no request-body or manual-caller contract change is needed. Preserve API-key authentication before lease/status disclosure. No headers remains valid for a manual profile caller, but a partial or supplied-invalid/expired/revoked lease pair must be rejected before publishing either command.
- The profile route does not by itself prove a ghost-root write: `SubjectCollectionEndpointMappings.ResolveAsync` requires an existing Horse read model and returns 404 if it is absent; `HorseAggregate.CollectJraProfile` throws if the aggregate is not registered, and `UpsertProfile` cannot register an unregistered Horse without both name fields (`HorseAggregate.cs`, `HorseAggregate.Collection.cs`). This is a guard on this route, not a general proof that every stale writer is fenced.
- Worker ordering matters. `CollectionPlatformWorkerClient.ExecuteAsync` acquires the task lease, pushes `CollectionWorkerLeaseContext` only around the handler, awaits `CollectAsync`, and then posts `CompleteAttemptAsync`; the JRA profile request is inside that handler. `AcquireAsync` rejects new task starts while the pipeline is paused and requires the current dispatch generation. Lambda `AcquireNextExecutionAsync` also returns `PipelinePaused` before acquiring a wake. `CompleteExecutionAsync` is different: it accepts a matching execution token/status without an expiry check and finalizes execution bookkeeping/releases unstarted dispatches. It runs after task processing; it is not itself proof of a profile write, but its post-drain behavior must remain covered so collection-store bookkeeping cannot be mistaken for source-store quiescence.
- The canonical `.github/workflows/app-deploy.yml` pauses collection and polls Running tasks at 10-second intervals for up to 60 attempts (10 minutes) before applying the Collector Lambda image. Failure leaves the pipeline paused and exits before the later API-stop job. Only after the Collector job succeeds does the deploy job stop the API, verify it is stopped, and check WAL/backup gates. `infra/collector-lambda/main.tf` configures a 900-second function timeout, reserved concurrency 1, batch size 1, and an event-source mapping to the function ARN (no alias is defined there). A Running task is marked terminal only after its handler returns, so a successful zero-Running drain is a meaningful gate for the profile side effect; if a worker exceeds the 10-minute drain bound, the workflow fails closed and does not proceed to API stop. This source ordering does not establish target-runtime `State`, `LastUpdateStatus`, resolved image digest, or absence of a still-finalizing invocation. Before any physical apply, use the existing GitHub AWS role path to verify the deployed function is Active, update status is Successful, and the expected image is current, with a bounded quiescence check before API stop. The present workflow source does not explicitly assert those Lambda metadata values; treat that as a required fence/deployment closure, not as already-proven evidence. Do not purge SQS or rely on a new permission, alias, or local AWS login.

## Typed coverage rule

At runtime compare each configured database's physical schema, indexes, triggers, migration/version markers, and required sidecars with its expected source model. Treat the 47-table inventory as a catalog, not proof of target presence or absence. Scan every configured surface, including the optional queue if configured; a missing required store, unknown object/column, unsupported version, or unclassifiable affected value blocks before the first source write. Preserve SQLite internal objects and schema history; classify rather than rewrite them.

## Bounded algorithm and invariants

1. Validate at most 16 unique canonical old Horse IDs and canonical JRA identities. Derive destination IDs only through the existing `DeterministicIdGenerator.BuildHorseId` using the recognized JRA-source URL form and assert the normalized source identity equals the accepted manifest identity before invoking it. Reject duplicate sources/destinations, self/cyclic maps, malformed IDs, and destination collisions. This phase proves syntactic mapping only, not identity truth.
2. Open all configured stores read-only/non-pooled/query-only and enumerate their actual physical schemas and required sidecars. Use keyset pages of at most 128 rows, parameterized bounded queries, JSON input limit 64 KiB and maximum depth 16. Keep a finite whole-run read/time budget; any exceeded budget marks the operation incomplete and prevents apply. Never load all rows or all event streams into memory.
3. Complete the full schema/root/reference/collision preflight before opening any source write transaction. Validate target Horse streams/snapshots, unique constraints, derived EntryIds, all typed reference closures, event replay, projections, and sidecar consistency. Record before/expected-after value hashes per typed row/page and counts; counts alone are insufficient. No cross-database atomicity is claimed.
4. Only after preflight is complete may a bounded store-at-a-time write begin. Keep durable operation progress outside the four source stores. Preserve unaffected fields byte/semantically as required by their serializer. Verify each transaction and then re-read/compare every selected typed reference; if interruption or a mismatch occurs, leave the system stopped/paused and mark partial/unverified. No automatic continuation, rollback by guessing, or resume.

The accepted operational journal ceiling is 64 MiB total and 1 MiB per operation/request/result, with 30-day terminal retention. Reserve space for failure/partial status; capacity exhaustion must stop safely before discarding evidence. These journal bounds do not relax source-store read/write bounds.
