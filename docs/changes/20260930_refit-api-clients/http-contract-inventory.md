# HTTP contract inventory

This inventory freezes the current server boundary for the Refit client work. It covers all **135 business routes** in [`route-inventory.md`](route-inventory.md); `/health` is excluded as a non-business probe. `http-contract-inventory.json` is the machine-readable per-route manifest, keyed by HTTP method and full path, and was extracted from each endpoint registration/handler, then cross-checked against API registrations and delegated handlers.

Each manifest item records the endpoint source file, input parameters by transport location (`path`, `query`, `queryObject` for `[AsParameters]`, or `body`), successful status/result expressions, declared `Produces<T>` metadata, and whether a successful response contains data. DI services and cancellation tokens are excluded from business inputs. `requestPresent=false` means the route has no path, query, or body input. `requestContractType` records the operation-specific Request contract; for a path-only Request its route identifier is ignored metadata, so `requestBodyPresent` remains false and no JSON body is sent. For inputs, a method parameter name/type is enough to trace its wire shape to the endpoint signature and request contract.

For implementation, define Refit inputs only for business parameters. A GET query object must preserve existing individual query names, omissions, defaults, multi-value representation, and DateOnly/DateTimeOffset binding. Route path values remain required method inputs. For output contracts, keep an operation-specific response wrapper when it carries receipt/progress/summary data; name entity data semantically (for example, `Race`/`RaceDto`, `Races`/`RaceSummaryDto[]`, or `Progress`/`ProgressDto`) and place the entity DTO under that property. A created ID or counts may remain direct response metadata. When the manifest says no successful payload, use no response DTO, even when status is 201 with a null Created body. When branches return both data and no-content, preserve the conditional branch and model the data return without inventing an empty object.

For each route, use `requestPresent`, `responsePresent`, and `successOutcomes` as the operation-specific presence decision; use `handlerParameters` and `successOutcomes[].payloadExpression` as the source of input/output mapping. A body that currently carries one entity or one multi-field business payload should become an input DTO property with the same semantic payload, while path identifiers and simple search/action metadata remain operation-level values. Data-bearing response expressions that represent detail/profile/history map to a semantic singular property over a `*Dto`; list/search expressions map to a plural property over a summary `*Dto`; progress, preview, inspection, dashboard, and repair-operation results keep their named data concept as a DTO property. Receipt IDs, counts, status flags, and similar operation metadata can remain direct only when they describe the operation result rather than fields of an entity. These are mapping categories, not permission to flatten or rename away fields recorded by the handler shape.

When moving existing DataAnnotations from a direct body model under a nested input DTO, retain the old validation outcome. Validate the nested object and its fields at the API boundary; a missing/null nested object must produce the existing client error class (normally 400), never fall through to a null dereference and 500. Do not assume nested validation is recursive unless the server binding and validation path proves it. This is especially relevant for bulk collection/race requests and repair manifests with field-level constraints.

## Shapes that require explicit attention

- `AcquireNextExecutionEndpoint` returns `CollectionExecutionAcquireResult` at 201 or 200 with a local serializer policy: web camel casing, null omission, `JsonStringEnumConverter(JsonNamingPolicy.CamelCase, allowIntegerValues: false)`. The rest of Minimal API JSON uses web defaults configured in `Program.cs` plus the JST DateTimeOffset converter; enums are numeric there. Do not reuse one enum serializer policy across these APIs without boundary-specific mapping. `CollectionExecutionAcquireStatus` and any other enum in that payload need string-valued wire equivalents or an explicit response conversion.
- `AcquirePredictionCandidateLeasesEndpoint` is conditional: 204 when no leases exist, 200 with leases otherwise. It is a data-bearing method with a no-content branch.
- `AcquireCollectionTaskEndpoint` returns 201 with a `CollectionTaskAcquireResult` containing the acquired lease; or 200 with a status result (including the `RepairHeld` case). Its nested lease/domain values are runtime types, not contracts to relocate.
- `CreateRaceOddsSnapshotEndpoint` returns `201 Created` with a null body. Keep the status/Location behavior but define no response DTO.
- Collection request/response values are currently spread across `CollectionOperations.CollectionPlatform`, `Api.CollectionController`, and `Contracts`. The manifest preserves the current top-level runtime response expressions for mapping, but implementation should create wire DTOs and convert at the endpoint boundary. Do not move EF or store models into Contracts.
- Collection task batch creation can return 202, 207, or 200 with `CollectionTaskBatchSubmissionResponse`; single task and backfill/recollection creation use 202 plus a Location. `SetCollectionPipeline` and internal lease transitions use 204. Keep status and payload branches intact.
- `Search*Request` values marked `queryObject` are `[AsParameters]`, so their contract fields bind from query values rather than a JSON body.
- Responses for horse/jockey/trainer profile and history APIs already map application read models into API DTOs (`HorseReadDto`, `JockeyDto`, `TrainerProfileResponse`, history response DTOs). Preserve that mapping boundary and the outer history/profile response semantics.
- Race entry repair endpoints delegate to `Api/CollectionController/RaceEntryRepairOperations`; the manifest includes those request/response shapes instead of marking the endpoints as unknown. Preview/apply payloads include source evidence and operation receipts as shown in the expressions. Its hold/fence operations return snapshots or a small fence object.

## Consumer evidence

Existing HTTP integration consumers are in Collector (`HttpRaceQueryService`, `HttpPredictionWriteService`, `HttpDataCollectionWriteService`, and collection/profile/identity/odds clients). Predictor consumes the existing race-query/prediction-write abstractions; Agents consume those abstractions through tools. Api's administration components use `AdminApiClient`, and some Api endpoint services use ApiClient abstractions for collection identity and repair operations. These establish why HTTP data semantics must remain stable while the approved operation-specific wrapper structure is introduced; the planned Refit client surface is not yet adopted by these callers.

The route ledger identifies the current endpoint file for every operation. The Refit implementation should be checked route-by-route against `http-contract-inventory.json`, especially where one route has both data and no-content success outcomes, where `Created` has no body, or where response models are internal to Api/CollectionOperations.

**Approval alignment:** Request DTO wrapper types and response wrapper names are new contract surface; existing wire semantics (method/path, business input values, body JSON fields, status, and returned data meaning) stay stable. Existing consumers will need adaptation to the new operation-specific wrappers. The inventory does not require existing consumers to keep their current CLR API surface.
