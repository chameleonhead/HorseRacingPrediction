## Context and goals

User explicitly requests SQL batch candidate retrieval with sequential processing, correction of full-backlog materialization, and proposals for other inefficiencies. Current source2f81ed32361daefcb1c10a47020e5708fd006c49: the minute scheduler selects at most500 due states then queries active tasks individually; dispatch reservation materializes all eligible task/resource rows to derive a lane set. Earlier bounded due query/index is already implemented, not this work's credit. Source findings support a query-work reduction, not a measured CPU percentage.

## Approved decisions

- Select A for this initial semantics-preserving patch: bounded SQL snapshot of the existing first500 due states including an EXISTS flag from collection_active_tasks. Evaluate the same policy sequentially, skip flagged states without extra queries, keep final RequestAsync deduplication. Leave existing GetDueStatesAsync and external snapshots unchanged. Close the reader before sequential requests; long WAL readers can obstruct checkpoint progress ([official SQLite WAL documentation](https://www.sqlite.org/wal.html)). This is a design risk, not a measured production lock diagnosis.
- B (exclude active tasks before ORDER/LIMIT500, refilling from later overdue targets) is a separate proposal. It can resolve the old window starvation but changes selected targets, query scanning and work creation, potentially exposing the separate existing failed-job rescheduling issue. No B implementation in this patch without a distinct explicit decision.
- Preserve final transactional RequestAsync deduplication because jobs may arrive after the snapshot. Sequential processing, existing policy and required revision remain unchanged.
- No active race repair holds: derive eligible lane membership in SQL DISTINCT instead of transferring the full eligible backlog, preserving the candidate guards and existing reservation transaction/predicates.
- Active holds: retain both heldTaskIds and current per-row MatchesHold resolution. Consume the eligible query as untracked rows, retain only distinct lanes and fully dispose its reader BEFORE fairness read/advance/reservation writes. Do not stop after seeing three lanes. This removes full eligible-list/EF tracking retention but does not remove all scans; the separate HeldTaskIdsAsync resource/history materialization remains unchanged and separately proposed.
- Other optimization proposals are ranked separately; no adjacent implementation without approval.
