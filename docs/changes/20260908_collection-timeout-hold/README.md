# 収集タイムアウトの失敗確定・実行保留と過去データ抽出の調査

- Status: Implemented
- Created: 2026-09-08
- Updated: 2026-09-08

## Context

利用者から、内部デッドライン到達もエラーとしてジョブ全体を停止すること、実行を明示的に保留できること、過去データ抽出ジョブが登録されない状況の調査を依頼された。

### 設計時に確認できた原因

- `CollectionExecutionService.RunSingleTaskAsync` は外側のキャンセル時に `RequeueCollectionTaskAsync` を呼び、Readyへ戻して正常にreturnする。14分の内部デッドラインに達しても失敗試行を確定しない。既存テスト `RunSingleTaskAsync_WhenCancelledByInternalDeadline_RequeuesInsteadOfFailing` もこの挙動を要求している。
- `Program.cs` の計画ジョブにも同じ再投入があり、こちらは例外を再送出する。単発収集と計画の終了結果が一致しない。
- CloudWatchを読み取り確認し、2026-09-08 04:42:05 JSTに `RaceResultCollection` / `JRA:race-result:2026-09-06` が内部デッドラインで中断し、次回再試行と記録されていることを確認。確認時のLambdaはActive、Timeout=900秒、SQS連携はEnabled。これだけではDB上の現在の全ジョブ状態や停止マーカーまでは断定できない。
- 既存の全体pauseはSQS/DLQをpurgeし、DBに停止マーカーを保存する。一方、API middlewareは内部状態RPCの書き込み全般を503で拒否するため、稼働中ジョブの完了・失敗報告まで拒否される。新規取得と結果報告の分離が必要。
- 過去レースの自動抽出は `NoOpHistoricalRaceReferenceCollector` がDI登録され、常に空の参照を返すため、`HistoricalRaceResultCollectionRequest` を作成できない。コメントもJRA再設計に伴う暫定無効化と明記している。
- `HistoricalDataRequestPlanner` は出馬表取得後に呼ばれ、馬・騎手・調教師の旧補完要求を条件付きで登録するが、旧 `HistoricalDataRequestExecutionService` とハンドラーのDI登録はコメントアウトされている。「すべての補完要求が登録されない」のではなく、過去レース参照の抽出停止と旧要求の実行停止が併存している。
- 馬詳細からの手動 `HorseHistoryDiscovery` → `HorseHistoryRace` は別の実装済み経路。旧自動Plannerはこの新経路に接続されていない。既存の[実装記録](../20260908_subject-refresh-horse-history/README.md)には隔離環境での検証があるが、今回、本番で手動実行はしていない。

## Goals

1. 内部デッドラインとジョブ単位のタイムアウトを失敗として記録し、自動再投入ループを止める。
2. 利用者が明示的に保留・解除でき、再起動や監視処理で保留が解除されないようにする。
3. 過去データ抽出の現状を正本文書に反映し、自動経路を復旧する場合の接続先を明確にする。

## Decisions

承認: 2026-09-08、改訂設計提示に対して利用者が「大丈夫です。よろしくお願いします」と明示承認。以降は実装・検証を継続する。

2026-09-08、利用者が以下の仕様を指定した。

- タイムアウト時は「収集処理全体を停止し、明示的な再開まで後続ジョブも実行しない」。
- 手動保留は「個別ジョブの保留・解除」「単一ジョブ向け・リースを拒否し、キャンセルし、保留」。

この指定に従い、初案の「実行中は保留不可」「集約親の未開始の子も保留」は撤回する。指定したジョブ1件だけを対象にし、実行中もキャンセルして保留できる設計へ変更した。新たな全体手動保留機能は追加せず、既存の全体停止・再開は維持する。改訂設計は上記のとおり承認された。

過去データについて今回の依頼は状況確認であり、自動復旧・大量の補完再登録は未実施。復旧する場合は旧Workerの再有効化ではなく、稼働中の馬起点履歴探索へ自動Plannerを接続する案を別途確定する。騎手補完や既存旧要求の移行、既存レースからのバックフィル範囲もその際に決める。

## Approved behavior

以下は利用者の指定を反映し、承認後に実装した設計。

- タイムアウトしたジョブはFailedにし、理由・期限・試行履歴・RequestIdを保存する。Readyへの自動復帰を行わない。Lambda側にもタイムアウトを失敗として返す。処理結果報告には処理用のキャンセル済みトークンを使わず、終了猶予内の独立した期限を設ける。
- 収集全体の停止理由を永続化し、後続の配送・新規リース取得を止める。既に取得済みの別ジョブは完了/失敗報告を受け付ける。実行中プロセスを強制終了する操作にはしない。
- 全体停止はキュー消去を必須にしない。全体再開と失敗ジョブのリランは別操作。再開だけで失敗ジョブを自動実行しない。
- 個別保留はPending/Ready/依存待ち/Runningで利用できる。対象は指定した1件だけで、親・子・同日の別ジョブへ保留を伝播させない。未開始のジョブはその場で保留となり、新規リースを拒否する。完了・失敗のジョブは保留対象外として理由を表示する。
- 実行中のジョブは保留要求を永続化し、新規リースを拒否したうえでWorkerへキャンセルを伝える。画面は「保留要求済み・中断待ち」と表示し、Workerが収集処理を中断して結果を報告した後に「保留中」へ移す。実行中保留は失敗や全体停止の原因にしない。
- キャンセルはブラウザー操作・HTTP・収集ループへ伝播する協調キャンセルとする。Workerは定期的に保留要求を確認し、正常な通信環境では5秒以内に検知する。既に保存済みのデータはロールバックしない。処理中断・後始末が終わる前に「保留完了」と表示しない。
- 保留要求と完了報告はサーバーで競合判定する。完了が先なら保留を拒否して最新状態を表示し、保留要求が先なら旧実行の完了報告で保留を解除しない。旧実行の中断を試行履歴に保存し、成功済みデータを維持する。
- Workerの応答がない間は中断待ちを維持し、解除を受け付けない。リース失効時に保留状態を確定できるようにするが、新しい実行は明示的な解除まで開始しない。古いリースによる結果報告は拒否する。
- 個別解除は元の待機条件を維持する。全体保留中に解除しても実行は始まらない。保留中の同一対象を新しい依頼として重複作成しない。
- 保留中の古いSQS通知はリースを取得できない。解除時に新しい配送世代を発行し、古い通知・監視・再スケジュール・依存解消による意図しない実行を防ぐ。
- 個別解除はWorkerの中断確認後、または旧リース失効後に受け付ける。中断した実行は新しいリースで再開し、利用可能なチェックポイントを再利用する。個別保留操作で既存の子を保留・キャンセルしない。親の依存解消が起きても、その親自身の保留は解除しない。

## Experience and interaction design

一覧の上部に収集全体の稼働/停止状態、手動/タイムアウトの理由、発生日時、原因ジョブへのリンクと既存の再開操作を表示する。個別保留・解除はジョブ詳細に置き、「この1件のみ。親・子ジョブには影響しません」と説明する。実行中は「保留して中断」、未開始は「保留」、中断確認後は「保留を解除」と表示する。中断待ちは解除を無効にして理由を説明し、状態を自動更新する。失敗・中断待ち・保留中を別の日本語ラベルで表示する。

## Acceptance criteria

停止範囲は収集全体、個別保留は指定した1件のみとする。

1. 収集・計画の内部デッドラインが失敗履歴に残り、Readyへ戻らず、同じ通知から再実行されない。
2. ジョブ単位のタイムアウトも同じ停止方針を適用する。ホストの通常終了と期限到達を区別する。
3. 全体停止後は次のジョブが開始せず、既に稼働中の有効リースの完了/失敗報告は成功する。再起動後も保留状態・理由が残る。
4. 全体停止と再開でSQS/DLQ消去や既存データ削除を要求しない。失敗ジョブは明示的なリランまで失敗のまま残る。
5. 個別保留中は配送・取得・再計画・監視・依存解消で実行されず、重複依頼も生成しない。解除時だけ元の条件に戻る。
6. 実行中の単一ジョブを保留すると、正常通信時5秒以内にWorkerがキャンセル要求を検知し、中断報告後に保留となる。中断待ちの解除を拒否し、Worker不在は旧リース失効後も保留を維持する。
7. 操作履歴・競合・不可理由、読み込み/空/エラー/送信中、360pxとキーボードでの操作を確認する。
8. 旧DBからの移行と既存の正常収集・未公開待機・手動リランの回帰を検証する。
9. 単一ジョブの保留では親・子・別ジョブは保留されない。親の依存解消でも保留は解除されない。全体再開でも個別保留は維持される。
10. 保留と完了・失敗・リース取得・解除の競合を検証し、旧実行の結果が保留を解除せず、解除後の実行を上書きしない。中断は試行履歴に残り、全体停止や失敗通知を引き起こさない。
