# Collection REST API: consumer and compatibility impact

This document inventories repository-owned consumers of the current collection API and records compatibility assumptions for the planned REST-oriented redesign. The inventory is based on source and test references present in the repository at the time of review. Repository search cannot establish whether separately deployed clients or operational scripts outside this repository use these routes.

**Cutover decision:** the compatibility recommendation below is historical investigation. The governing `README.md` requires every canonical route under `/api/v2/`, no aliases, removal of all first-party old-route literals, and 404/405 checks for retired pairs. External consumers remain unobservable from this repository and are an explicitly accepted proposal risk; the change record remains Proposed pending user approval.

## Current boundaries

`CollectionController` is a directory/namespace name, not an MVC controller. The HTTP surface is Minimal API code in `src/HorseRacingPrediction.Api/CollectionController/`, registered independently from the common API endpoint modules in `Program.cs`.

The principal collection-platform extension maps the admin surface under `/api/admin/collection` and the worker protocol under `/api/internal/collection`. Admin route groups are tagged `Collection Platform` and worker routes `Collection Worker`. The groups have no separate visible authorization declaration. `Program.cs` installs API-key protection middleware globally; the API key is also described in OpenAPI. This evidence does not establish distinct admin and worker identities or roles. Do not imply that route prefixes alone enforce different authorization.

DTO ownership is split today:

- Collection state, task, request, receipt, backfill, worker, and revision models are mostly in `HorseRacingPrediction.CollectionOperations.CollectionPlatform.CollectionModels`.
- Batch request/response contracts are in `HorseRacingPrediction.Contracts`.
- Several API-facing request and response types are declared at the bottom of `CollectionPlatformEndpointExtensions.cs` (including backfill, revision, migration, recovery, and worker-completion DTOs).
- Admin UI consumption is mediated by `AdminApiClient`; Collector request and worker traffic use separate clients.

Keep shared wire DTO ownership stable during route migration unless changing a payload is an explicitly approved part of the design.

## Repository-owned versus unknown consumers

Repository-owned consumers found by route/client search are the two AdminApiClient collection partials and their Blazor pages, `CollectionRequestApiClient`, `CollectionPlatformWorkerClient`, their API/Collector tests, the local entry-repair script, and design documentation. `Program.cs` registers each route module for both production and test-host patterns where applicable.

No dedicated external SDK, OpenAPI-generated client, or separate service definition was found in the searched source tree. This is not evidence that no external consumer exists: route usage in other repositories, deployed old binaries, operator-maintained scripts, or direct HTTP calls cannot be enumerated here. The API is protected by configured API-key middleware, and `AdminApiClient` sends that key; this indicates authenticated usage, not the identity or number of consumers.

## Canonical merged consumer contracts

- Revision and race-period recollection calls from the AdminApiClient converge on `POST /api/v2/admin/collection/recollection-batches`. The body discriminator is `mode=Revision` with definition/revision/lane/priority or `mode=RacePeriod` with provider/date range. Retain `CollectionRevisionEndpointTests.cs`, `CollectionOperationsEndpointTests.cs`, and `CollectionPlatformDiscoveryEndToEndTests.cs` coverage for both modes, replay and validation.
- Execution start and completion calls from `CollectionPlatformWorkerClient` converge on `PATCH /api/v2/internal/collection/execution-batches/{id}` with `transition=Start|Complete`; both carry lease token and generation, and completion retains its evidence payload. Verify through `CollectionPlatformWorkerClientTests.cs`, `CollectionCompletionTransportTests.cs`, and `CollectionPlatformDiscoveryEndToEndTests.cs`, including stale-token and duplicate-completion cases.
- The full canonical methods, paths, mode contracts, consumer evidence, and retired-route 404/405 checks are enumerated in the governing `README.md`; this document's route literals above are current-state discovery evidence only.

## HTTP method and status guidance

Current resource reads use `GET`; asynchronous work creation returns `202 Accepted`; bodyless successful state transitions commonly return `204 No Content`; invalid input, missing targets, and stale/incompatible state currently map to `400`, `404`, and `409`. Preserve those observable outcomes while route paths are reorganized unless a status change is separately specified and tested.

For resource-oriented design, RFC 9110 defines safe methods as essentially read-only and says `PUT`, `DELETE`, and safe methods are idempotent; `POST` processes the enclosed representation according to the target resource's semantics. This supports GET for reads, POST for creating collection requests/operation-run resources, and PUT/PATCH for changing a known state resource. [RFC 9110, HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110/).

Microsoft's Minimal API tutorial demonstrates CRUD routes using GET, POST, PUT/PATCH, and DELETE, with PUT replacing a known resource and PATCH representing partial updates. [Create a Minimal API with ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/tutorials/min-web-api?view=aspnetcore-10.0). This is guidance for route semantics; it does not determine this service's idempotency, 202/204 policy, or deployment compatibility.
