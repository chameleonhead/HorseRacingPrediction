## Context

The Collection API is Minimal API code, not an MVC controller. It has 65 routes registered from six sources under `CollectionController/`, plus 4 adjacent PredictionScheduling routes. Repository-owned consumers include AdminApiClient/Blazor, Collector request and worker clients, API/Collector tests, and a local repair script. Source cannot establish whether external callers exist.

`route-map.md` and `consumer-impact.md` retain the source inventory and caller detail. This README repeats every exact current method/path and proposed contract so the governing proposal is independently reviewable.

## Goals

- Replace all 65 CollectionController-derived routes and all 4 PredictionScheduling routes with the route contracts below, except CP-24 which is deleted after proving it is unused by first-party HTTP callers.
- Use operation-per-file endpoints under `Endpoints/<Feature>/<Operation>Endpoint.cs`, composed by `Extensions/EndpointExtensions.cs`.
- Delete every old route registration and first-party literal for old method/path pairs. Retain no compatibility aliases. Verify each retired pair returns 404 or 405. Where an old URI would otherwise be reused unchanged, move the canonical endpoint to a distinct URI so rejection is observable.
- Preserve request modes, filters, selectors, payload fields, response outcomes, idempotency and per-item results, plus API-key protection, route-specific filters, locks, pause/drain checks, lease tokens, generation/fingerprint fences and stale-preview guards.
- A merge removes a duplicate source registration, not unique behavior; merged filters/modes/selectors retain the behavior of both routes.

## Non-goals

- MVC conversion or persistence/domain/event redesign; new authorization roles.
- Folding cross-store domain writes into completion or claiming atomicity across stores.
- Envelope-wide acquire/report: excluded follow-up because lease ownership and cross-store recovery are unproven.
- Changing existing history batching.

### Collector fanout baseline

Let R be outbound race-discovery request items and D be outbound date-discovery request items in one run. They are separate items; a race may contribute one item to each set, so R + D counts request items, not distinct races. Baseline unbatched submissions are C₀ = R + D. Batch the combined item stream under the existing maximum-500 semantics: C₁ = ceil((R + D) / 500); expected calls avoided = (R + D) - ceil((R + D) / 500). Preserve deterministic batch/item keys, one result per item, partial failures and replay idempotency. Keep current history batching. This reduces transport calls; it does not promise atomic persistence.

Do not combine cross-store domain writes with task completion or claim atomic commits. Keep envelope-wide acquire/report excluded pending evidence on lease ownership and cross-store recovery.

## Decisions and boundaries

1. All 69 registrations are in scope, including PredictionScheduling.
2. No compatibility aliases. Remove old registrations and old first-party literals; assert retired old method/path pairs return 404/405. Do not leave deployed first-party binaries that require retired paths.
3. Preserve existing payloads and outcomes except route/path/mode convergence specified above. Previews remain ephemeral.
4. Keep global API-key middleware and all route-specific guard behavior; prefixes do not imply separate authorization.
5. Removing duplicate registrations in a merge is distinct from deleting behavior; the combined endpoint must retain all behaviors.
6. External callers and atomic deployment cannot be proven from source. Accept the user-directed no-alias risk, coordinate first-party deployment, and monitor rejected legacy calls. If coordinated cutover is unavailable, return the design to Proposed for a revised contract.
