## Context and authorization

The user requests efficiency improvements and permits behavior-changing work only when benefit is expected and the change is appropriate. The preceding investigation identified two bounded inefficiencies: identical execution-lease count/list queries and scheduled-state filtering after unbounded materialization. This record replaces the unapproved five-second interval/index design in [the investigation record](../20261005_collection-cpu-load/README.md). The historical [loop inventory](../20261005_collection-cpu-load/evidence/service-loop-inventory.md) remains evidence at revision09566e95, not proof of implementation or live CPU attribution.

The implementation contract preserves the one-second dispatcher interval, all service registrations and clocks, prioritization, capacity, lease expiry, transactions, hold handling, recovery and duplicate prevention. No UI/API/domain contract change, service removal, hosting change, data repair, bulk retry or failure dismissal. The conditional index gate is now satisfied for one nonunique NextCollectionAt-leading state index: actual EF query scans/sorts with the old index; an isolated comparison of its exact SQL range-searches without a sort using the candidate. An additive schema24 migration is separately recorded below before implementation. Removing duplicate queries and bounding materialization/ranged lookup are mechanical outcomes; total CPU reduction is not guaranteed without process profiling.
