# 過去レースの自律バックフィル

- Status: Proposed
- Owner: HorseRacingPrediction team
- Created: 2026-09-09
- Updated: 2026-09-09

## Context

現在の自動成績収集は、JST の当日から5日前までを対象とし、日別完了状態が `Complete` の日を再登録しない。馬詳細から明示的に依頼すれば、その馬の出走履歴を起点に過去レースを取得できるが、利用者の操作が必要であり、登録済みの馬に関係するレースへ対象が偏る。

過去結果向けには `ResultBackfillPlanningRequest`、月・日単位の探索ジョブ、`InitialResultBackfillYears` など旧設計の型と設定が残っている。しかし、旧 URL 列挙方式の廃止後は登録・実行が無効であり、現行の `JraSession` / `JraNavigator` 経路には移行されていない。したがって、直近5日より前のレースを網羅的かつ自律的に増やす経路は現在存在しない。

この変更では、通常開催日の収集を妨げず、停止・再開可能で、取得範囲と未完了箇所を説明できる自律バックフィルを設計する。

## Goals

- JRA の過去レース結果を、利用者の個別操作なしで継続的に取得する。
- 通常の出馬表・当日および直近結果・利用者が明示した再取得を優先する。
- 新しい過去日から古い日へ進め、早期に予想・分析へ有用な範囲を広げる。
- 再起動、Lambda の単発実行、重複通知、部分失敗があっても、完了済みの開催日を維持して続きから再開する。
- 対象期間、進捗、未完了理由を既存のジョブ・日別収集状態から確認できるようにする。

## Non-goals

- 地方競馬・海外競馬など JRA 以外のデータソースは対象にしない。
- JRA が公開していない期間や情報を別サイトから補完しない。
- 過去レースを定期的に全面再取得して訂正を検知する機能は含めない。
- 馬・騎手・調教師プロフィールの全件自動更新は含めない。
- 馬起点の手動履歴取得、レース詳細からの手動再取得は廃止しない。
- 初回リリースで専用の新しい管理画面は作らない。

## Experience and interaction design

自律バックフィルは Collector の通常サイクルで計画され、管理者による開始操作を要求しない。既存の「収集を停止」はバックフィルを含むすべての新規実行を止め、「再開」は保存済みカーソルと日別状態から処理を再開する。個別ジョブの保留・再実行も既存操作を使用する。

管理者は既存のジョブ一覧と日別成績収集状況で、少なくとも次を確認できる。

- 対象日、状態、試行回数、最終エラー
- 完了済みレース数と想定レース数
- 自律バックフィル由来であること
- 現在のバックフィル対象期間と、次に探索する日付

初回リリースでは上記情報を既存のジョブ詳細・状態 API に載せる。専用の進捗画面は、実運用で一覧性が不足すると確認されてから別変更として検討する。

## Navigation and relationships

```text
定期 CollectionPlanning
  ├─ 通常の予定・直近結果ジョブを登録
  └─ バックフィル計画（1サイクルの上限内）
       ├─ 保存済みカーソルから新しい順に候補日を選択
       ├─ JRA 開催日だけ RaceResultCollection を登録
       └─ 完了・除外・再試行状態を保存してカーソルを進める

RaceResultCollection
  └─ 現行の結果取得・API 登録・RaceDataCollectionStatus 更新を再利用
```

バックフィル専用の結果取り込み処理は作らず、起点と優先度だけを区別する。これにより、通常収集と過去収集で抽出・正規化・永続化の挙動が分岐することを避ける。

## Technical impact

### 取得方式

採用案は、日付を主キーとするローリングバックフィルである。

1. JST の「直近自動収集範囲より前の日」から開始する。
2. `InitialResultBackfillYears`（既定3年）を初期下限とする。期間の定義は「実行日から年数を減算した日」までとし、境界日を含む。
3. 新しい日から古い日へ、月をチェックポイント単位として探索する。
4. 現行の JRA 開催日探索で開催を確認し、開催日のみ既存 `RaceResultCollection` を登録する。
5. `ResultDayCollectionState.Complete` の日は登録しない。不完全・失敗日は上限付きで再試行し、上限到達後も未完了として記録したうえでカーソル全体は先へ進める。
6. 下限到達後は定期計画で無駄に全期間を走査せず、直近範囲との隙間だけを確認する。対象期間を延長する設定変更時は、保存済み下限から続行する。

1回の計画で探索・登録する量には上限を設ける。既定案は「1か月、かつ開催日4日まで」とし、設定で調整可能にする。月内に未処理日が残る場合は同じ月のチェックポイントから再開する。

### 優先順位と実行抑制

優先度は数値の大きいものを先にする。具体値は既存値との互換を保ちながら実装時に定数化するが、順序は次を契約とする。

| 順位 | 処理 | 理由 |
|---:|---|---|
| 1 | 収集計画、利用者が明示した再取得・プロフィール/履歴更新 | 軽量な計画を滞留させず、利用者操作へ速やかに応答するため |
| 2 | 当日・直近開催のうち、自動更新が必要な出馬表 | 予想生成前の入力を確保するため。発走済み・結果取得済みは [出馬表の終端設計](../20260909_stop-redundant-racecard-collection/README.md) に従って対象外とする |
| 3 | 当日・直近開催の確定結果、未完了日の再試行 | 結果反映と予想評価を遅らせないため |
| 4 | 自律バックフィルの開催日探索・結果収集 | 余剰能力で徐々に網羅性を高める処理だから |

現在の常駐実行はジョブ種別を固定順で巡回するため、ジョブ種別をまたぐ数値優先度が厳密には効かない。実装では実行可能な収集ジョブを横断して優先度順に選択するか、同等の前景優先制御を導入する。SQS / Lambda 経路でも、バックフィル登録前に前景ジョブの滞留を確認し、前景ジョブがある間は新しいバックフィルを増やさない。

`SuppressHistoricalBackfillDuringLive=true` の場合、開催中モードではバックフィルの新規計画を止める。すでに配送済みの1件は安全に完了させ、強制キャンセルはしない。全体停止・個別保留・タイムアウトの規則は既存設計を継承する。

### 状態と冪等性

- 既存の日別状態を取得済み判定の正本とする。
- バックフィル計画には、対象上限・対象下限・次の候補日・最終計画時刻を永続化する。
- 通常収集とバックフィルで同じ日付のジョブキーを共有し、同時登録を重複抑止する。
- 取得由来には `Scheduled` と区別できる `HistoricalBackfill` を記録する。通常収集が同じ日を先に完了した場合は、その完了を採用する。
- 開催なしは成功した探索結果としてチェックポイント化し、毎サイクル再照会しない。
- ページ未公開・一時的通信障害は再試行可能、恒久的な対象外・公開範囲外は除外、解析異常は未完了として区別する。
- 1日内の一部競馬場・レースに失敗があれば日別状態を `Incomplete` とし、成功済み結果は冪等に保持する。

### 設定

既存 `InitialResultBackfillYears` と `SuppressHistoricalBackfillDuringLive` を有効な設定として利用する。加えて、機能の有効化、1サイクルの最大開催日数、日別最大試行回数を設定可能にする。安全な導入のため、コード実装と検証環境では有効、本番設定はデプロイ時に明示的に有効化できる構成とする。

## Decisions

### 採用: 日付単位の新しい順のローリングバックフィル

- 網羅率を日別状態で測定できる。
- 既存の `RaceResultCollection` と結果取り込みを再利用できる。
- 直近のデータほど予想・検証への効用が高く、途中段階でも価値が出る。
- 月チェックポイントと日ジョブの組み合わせで、再開と部分再試行を両立できる。

### 不採用: 馬の出走履歴だけを起点に自動展開

既存馬に関係するレースへ偏り、未登録馬だけが出走したレースを発見できない。循環的に対象が増えて負荷上限も説明しにくいため、手動の対象更新経路として維持する。

### 不採用: 起動時に対象期間の全日を一括登録

数年分のジョブと通知が一度に増え、通常収集の遅延、JRA への急激なアクセス、運用画面の見通し低下を招く。小さい上限で継続的に計画する。

### 不採用: 無効化された旧バックフィル Worker をそのまま復活

削除済みの URL 列挙方式へ依存し、現行 JRA ナビゲーションと二重の取得実装になる。旧ジョブ型・設定は移行時の互換確認には使うが、実行経路は現行の日別収集へ統合する。

### 保留: 3年より前への拡張

初回の既定範囲を3年とし、処理時間、失敗率、JRA 公開範囲、分析上の有用性を確認してから別途拡張する。設計上は下限設定の変更で続行できる。

## Acceptance criteria

- 機能が有効な環境では、利用者操作なしに、直近5日範囲より前の JRA 開催日が新しい順で結果収集対象になる。
- 初期下限は `InitialResultBackfillYears` で制御され、既定3年の境界日を含む。
- 開催なしの日と日別状態が `Complete` の日は結果収集ジョブを登録しない。
- 通常収集とバックフィルが同じ日を計画しても、有効な日別結果収集ジョブは重複しない。
- 当日・直近収集または利用者起点ジョブが Ready / Running の間、バックフィルの新規登録または次ジョブ実行がそれらを追い越さない。
- 開催中モードで抑制設定が有効な場合、新しいバックフィルを計画しない。
- 1回の計画で登録されるバックフィル開催日数が設定上限を超えない。
- Collector の再起動、同じ計画の再実行、重複通知の後も、完了日と開催なし日を再処理せず保存済み位置から続行する。
- 一部失敗の日は `Incomplete` と成功件数を保持し、上限まで再試行する。上限到達後も他の日のバックフィルは進行する。
- ジョブ詳細または日別状態から、対象日、バックフィル由来、進捗、最終失敗理由を確認できる。
- 常駐モードと `--once` / Lambda モードの双方で、同じ計画・優先順位・冪等性が成立する。
- 既存の直近結果収集、出馬表収集、手動レース再取得、馬起点履歴取得、停止・保留・再開に回帰がない。

## Delivery plan

1. バックフィルのカーソル・由来・設定契約を CollectionOperations に追加し、状態ストアの移行と単体テストを行う。
2. 現行 JRA スケジュール・結果ナビゲーションを使う月チェックポイント型プランナーを実装し、開催なし・完了済み・不完全日の判定をテストする。
3. バックフィルも既存 `RaceResultCollection` で実行し、由来と日別状態を記録する。
4. 常駐モードでジョブ種別横断の前景優先を保証し、Lambda 計画時の滞留抑制を追加する。
5. 再起動、部分失敗、上限到達、Live 抑制、重複計画を統合テストする。
6. 検証環境で小さい期間・上限から実サイト確認し、アクセス量と所要時間を測定する。
7. 正本ドキュメント、設定、本番デプロイ値、検証記録を同期する。

各段階は関連テスト、ビルド、`git diff --check`、`git status` を確認し、単独で検証可能なチェックポイントとしてコミットする。
