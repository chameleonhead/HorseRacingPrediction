# 過去レースと馬公式情報の自律収集

- Status: Approved
- Owner: HorseRacingPrediction team
- Created: 2026-09-09
- Updated: 2026-09-09

## Context

現在の自動成績収集は、JST の当日から5日前までを対象とし、日別完了状態が `Complete` の日を再登録しない。馬詳細から明示的に依頼すれば、その馬の出走履歴を起点に過去レースを取得できるが、利用者の操作が必要であり、登録済みの馬に関係するレースへ対象が偏る。

過去結果向けには `ResultBackfillPlanningRequest`、月・日単位の探索ジョブ、`InitialResultBackfillYears` など旧設計の型と設定が残っている。しかし、旧 URL 列挙方式の廃止後は登録・実行が無効であり、現行の `JraSession` / `JraNavigator` 経路には移行されていない。したがって、直近5日より前のレースを網羅的かつ自律的に増やす経路は現在存在しない。

また、現行の出馬表収集後に動く `HistoricalDataRequestPlanner` は、馬・騎手・調教師の旧補完要求を登録するが、その実行Workerは無効である。一方、管理画面から利用できる `SubjectProfileRefresh` / `HorseHistoryDiscovery` / `HorseHistoryRace` は、現行JRAナビゲーションで馬の公式プロフィールと全掲載履歴を取得できる。この稼働中経路は自動計画へまだ接続されていない。

この変更では、今週末の出走予定馬の公式情報を最優先にしつつ、通常開催日の収集を妨げず、停止・再開可能で、取得範囲と未完了箇所を説明できる自律収集を設計する。

## Goals

- JRA の過去レース結果を、利用者の個別操作なしで継続的に取得する。
- JRAのレースから判明した馬について、JRA公式プロフィールとJRA掲載の出走履歴を自律的に取得する。
- 今週末の出馬表と、その出走予定馬の最新公式情報を最優先で揃える。
- 出走予定馬の同定可能な公式情報を推測せず取得し、取得不能値で既存値を消さない。
- 通常の当日・直近結果と利用者が明示した再取得を、長期バックフィルより優先する。
- 新しい過去日から古い日へ進め、早期に予想・分析へ有用な範囲を広げる。
- 再起動、Lambda の単発実行、重複通知、部分失敗があっても、完了済みの開催日を維持して続きから再開する。
- 対象期間、進捗、未完了理由を既存のジョブ・日別収集状態から確認できるようにする。
- 長期化する自律収集について、永続化された定期見直しジョブが優先順位・滞留・不足・次回投入量を再評価する。

## Non-goals

- 地方競馬・海外競馬など JRA 以外のデータソースは対象にしない。
- JRA が公開していない期間や情報を別サイトから補完しない。
- 過去レースを定期的に全面再取得して訂正を検知する機能は含めない。
- 出走または収集済みレースとの関係がないJRA登録馬を、名鑑全体から全件探索する処理は含めない。
- 騎手・調教師プロフィールの全件自動更新は含めない。
- 馬起点の手動履歴取得、レース詳細からの手動再取得は廃止しない。
- 初回リリースで専用の新しい管理画面は作らない。

## Experience and interaction design

自律バックフィルは Collector の通常サイクルで計画され、管理者による開始操作を要求しない。既存の「収集を停止」はバックフィルを含むすべての新規実行を止め、「再開」は保存済みカーソルと日別状態から処理を再開する。個別ジョブの保留・再実行も既存操作を使用する。

管理者は既存のジョブ一覧と日別成績収集状況で、少なくとも次を確認できる。

- 対象日、状態、試行回数、最終エラー
- 完了済みレース数と想定レース数
- 自律バックフィル由来であること
- 現在のバックフィル対象期間と、次に探索する日付
- 馬ごとの公式プロフィール取得時刻、公式出走履歴の発見・成功・失敗・対象外件数
- 今週末出走馬由来か、通常・過去レース由来か

初回リリースでは上記情報を既存のジョブ詳細・状態 API に載せる。専用の進捗画面は、実運用で一覧性が不足すると確認されてから別変更として検討する。

## Navigation and relationships

```text
定期 CollectionPlanning
  ├─ 今週末の出馬表ジョブを登録
  │    └─ 出走予定馬ごとに公式情報ジョブを登録
  │         ├─ SubjectProfileRefresh（最新プロフィール）
  │         └─ HorseHistoryDiscovery（JRA全掲載履歴）
  │              └─ HorseHistoryRace（履歴レースの取得）
  ├─ 通常の予定・直近結果ジョブを登録
  └─ バックフィル計画（1サイクルの上限内）
       ├─ 保存済みカーソルから新しい順に候補日を選択
       ├─ JRA 開催日だけ RaceResultCollection を登録
       └─ 完了・除外・再試行状態を保存してカーソルを進める

RaceResultCollection
  ├─ 現行の結果取得・API 登録・RaceDataCollectionStatus 更新を再利用
  └─ 新たに判明した馬の公式情報を低優先度で補完

AcquisitionPlanReview（定期見直しジョブ）
  ├─ 今週末の出馬表・馬公式情報の不足を最優先で再確認
  ├─ Ready / Running / Waiting / Failed とチェックポイントを集計
  ├─ 次サイクルの優先度・投入上限・バックフィル抑制を更新
  └─ 判断理由・変更内容・次回見直し時刻を保存
```

バックフィル専用の結果取り込み処理は作らず、起点と優先度だけを区別する。馬公式情報も、実装済みの手動取得と同じ現行ジョブ・JRAナビゲーションを再利用する。これにより、自動・手動、通常・過去収集で抽出・同定・正規化・永続化の挙動が分岐することを避ける。

## Technical impact

### 取得方式

採用案は、日付を主キーとするローリングバックフィルである。

1. JST の「直近自動収集範囲より前の日」から開始する。
2. `InitialResultBackfillYears`（既定3年）を初期下限とする。期間の定義は「実行日から年数を減算した日」までとし、境界日を含む。
3. 新しい日から古い日へ、月をチェックポイント単位として探索する。
4. 現行の JRA 開催日探索で開催を確認し、開催日のみ既存 `RaceResultCollection` を登録する。
5. `ResultDayCollectionState.Complete` の日は登録しない。不完全・失敗日は上限付きで再試行し、上限到達後も未完了として記録したうえでカーソル全体は先へ進める。
6. 下限到達後は定期計画で無駄に全期間を走査せず、直近範囲との隙間だけを確認する。対象期間を延長する設定変更時は、保存済み下限から続行する。

1回の計画で探索・登録する量には上限を設ける。既定案は「1か月、かつ開催日4日まで」とし、設定で調整可能にする。月内に未処理日が残る場合は同じ月のチェックポイントから再開する。

### 馬ごとのJRA公式情報

対象は、出馬表または収集済みJRAレースから内部馬IDとJRA上の同一性を確認できる馬とする。取得項目は現行の馬公式情報経路と同じく、JRAが対象ページで公開する馬名、性別、生年月日、毛色、血統、生産者、産地、馬主、調教師、公開識別子、出典URL、取得時刻、およびページ送りを含む全掲載出走履歴とする。JRAが公開しない値は推測せず、空値で既存値を消さない。現在プロフィールで過去レース時点の馬主・調教師を上書きしない。

取得対象は価値と負荷に応じて次の3群に分ける。

1. **今週末の出走予定馬**: 出馬表で判明した全馬について、既存データの有無にかかわらず、その開催週に公式プロフィールと全掲載履歴を1回更新する。プロフィール、履歴探索、直近5走の不足レースを前景処理とし、それより古い掲載履歴は当日・直近結果を妨げない順位で継続する。失敗・中断時は成功済みページとレースを維持して再開する。
2. **当日・直近結果で新たに判明した馬**: 公式プロフィールまたは履歴が未取得の場合に自動補完する。今週末対象より低く、長期バックフィルより高い優先度とする。
3. **長期バックフィルで新たに判明した馬**: 公式プロフィールまたは履歴が未取得の場合に、レース日バックフィルと同じ低優先度・件数上限内で補完する。

「今週末」はJST基準で、現在日から7日以内の直近の土曜・日曜開催とする。祝日等のJRA開催が同じ期間にある場合も、その開催日を同じ最優先群へ含める。開催週に一度成功した馬は、出馬表が再取得されるたびに全履歴を再探索しない。公開識別子と取得週を含む冪等キーで重複を抑止し、新しい開催週、手動再取得、または前回失敗時だけ再実行する。

履歴探索から発見した各レースは新しい順に子ジョブ化する。同じ履歴レースを起点として他の全出走馬の履歴をさらに高優先度で再帰展開しない。レース結果から初めて判明した別馬は上記2または3の通常上限へ戻し、無制限な連鎖を防ぐ。

### 定期的な作業見直しジョブ

自律収集全体が数時間から数日継続することを前提に、`AcquisitionPlanReview`（名称は実装契約上の仮称）を独立した永続ジョブとして定期登録する。単なる `BackgroundService` の内部タイマーにせず、通常のジョブと同様に状態、試行、開始・終了、判断結果を保存し、常駐・`--once` / Lambda の双方で同じ処理を実行する。

既定の見直し間隔は15分とし、同一時間枠では1件だけを登録する。前回見直しが実行中なら重複登録せず、その完了後の次時間枠で再評価する。全バックフィル完了後も見直しは継続し、新しい開催週、設定範囲の延長、未完了の再発を検出する。変更がなければ成功した no-op として記録する。

見直しジョブは次を評価する。

- 今週末開催の出馬表が取得・更新対象として不足していないか。
- 今週末出走馬のプロフィール、履歴探索、直近5走に未取得・失敗・待機がないか。
- 当日・直近結果の未完了が長期バックフィルより後ろに滞留していないか。
- ジョブ種別横断の Ready / Running / WaitingDependency / Failed / DeadLetter 件数と最終進捗時刻。
- 月・日・馬履歴のチェックポイントが進んでいるか、同じ対象で失敗が反復していないか。
- 現在時刻、開催モード、キュー深さ、設定上限に対して新しい低優先度ジョブを投入してよいか。

評価結果に基づき、未登録の前景ジョブを冪等登録し、未実行ジョブの優先度を最新の開催近接度へ更新し、長期バックフィルの次回投入量を減少・停止・通常値へ戻す。古くなった計画上の候補はキャンセルせず、未配送かつ未実行なら新しい優先度と抑制規則を適用する。

見直しジョブは実行中ジョブのリースを奪わず、強制キャンセルせず、成功済み処理をやり直さない。タイムアウトで全体停止中、手動保留中、DLQサーキットブレーカー作動中は、新規投入や自動再開を行わず、状況と推奨される次の確認事項だけを保存する。Failed / DeadLetterを無条件に再投入せず、既存の再試行上限と手動再開契約を守る。

既存 `CollectionJobWatchdogService` はリース切れと配送漏れを機械的に修復する基盤監視として維持する。`AcquisitionPlanReview` は何を優先し次に計画するかを再判断する業務ジョブであり、watchdogの再ディスパッチ責務を重複実装しない。

### 優先順位と実行抑制

優先度は数値の大きいものを先にする。具体値は既存値との互換を保ちながら実装時に定数化するが、順序は次を契約とする。

| 順位 | 処理 | 理由 |
|---:|---|---|
| 1 | 収集計画、定期見直し、利用者が明示した再取得 | 軽量な計画・再評価を滞留させず、利用者操作と最新優先順位へ速やかに応答するため |
| 2 | 今週末開催のうち、自動更新が必要な出馬表 | 予想対象と出走馬を最初に確定するため。発走時刻到達・公式結果確認後は [出馬表の取得終了設計](../20260909_stop-redundant-racecard-collection/README.md) に従って対象外とする |
| 3 | 今週末の出走予定馬の公式プロフィール・履歴探索・不足している直近5走 | 週末予想へ正確な馬情報と直近成績を先に供給するため |
| 4 | 当日・直近開催の確定結果、未完了日の再試行 | 結果反映と予想評価を遅らせないため |
| 5 | 今週末出走馬の直近5走より古い全掲載履歴 | 当日結果を塞がず、対象馬の公式履歴を完全化するため |
| 6 | その他の直近出馬表、当日・直近結果で未取得の馬公式情報 | 将来開催と新規馬の情報を継続的に整えるため |
| 7 | 自律バックフィルの開催日探索・結果収集・未取得馬公式情報 | 余剰能力で徐々に網羅性を高める処理だから |

現在の常駐実行はジョブ種別を固定順で巡回するため、ジョブ種別をまたぐ数値優先度が厳密には効かない。実装では実行可能な収集ジョブを横断して優先度順に選択するか、同等の前景優先制御を導入する。SQS / Lambda 経路でも、バックフィル登録前に前景ジョブの滞留を確認し、前景ジョブがある間は新しいバックフィルを増やさない。

今週末出馬表または出走予定馬の公式情報ジョブが Ready / Running / 再試行待ちの間、長期バックフィルの新規登録を止める。`SuppressHistoricalBackfillDuringLive=true` の場合、開催中モードでもバックフィルの新規計画を止める。すでに配送済みの1件は安全に完了させ、強制キャンセルはしない。全体停止・個別保留・タイムアウトの規則は既存設計を継承する。

### 状態と冪等性

- 既存の日別状態を取得済み判定の正本とする。
- バックフィル計画には、対象上限・対象下限・次の候補日・最終計画時刻を永続化する。
- 通常収集とバックフィルで同じ日付のジョブキーを共有し、同時登録を重複抑止する。
- 取得由来には `Scheduled` と区別できる `HistoricalBackfill` を記録する。通常収集が同じ日を先に完了した場合は、その完了を採用する。
- 開催なしは成功した探索結果としてチェックポイント化し、毎サイクル再照会しない。
- ページ未公開・一時的通信障害は再試行可能、恒久的な対象外・公開範囲外は除外、解析異常は未完了として区別する。
- 1日内の一部競馬場・レースに失敗があれば日別状態を `Incomplete` とし、成功済み結果は冪等に保持する。
- 馬公式情報は対象馬ID・操作・対象開催週で重複抑止し、手動依頼は別の明示的な実行として履歴を保持する。
- プロフィールと履歴探索を別ジョブにし、一方の失敗で他方の成功を取り消さない。履歴の成功済み子レースも再試行時に維持する。
- 見直しジョブは時間枠を含む冪等キーと見直し世代を持ち、同じ世代の古い判断で新しい優先順位や抑制状態を上書きしない。
- 見直し結果には評価時刻、対象範囲、状態別件数、最終進捗、優先度変更、追加・抑制件数、判断理由、次回予定を保存する。

### 設定

既存 `InitialResultBackfillYears` と `SuppressHistoricalBackfillDuringLive` を有効な設定として利用する。加えて、機能の有効化、1サイクルの最大開催日数、日別最大試行回数、1サイクルの低優先度馬数、見直し間隔（既定15分）、進捗停滞とみなす期間を設定可能にする。今週末出走馬には低優先度馬数の上限を適用せず全頭を計画するが、同時実行数とJRAアクセス間隔は共通制限を守る。安全な導入のため、コード実装と検証環境では有効、本番設定はデプロイ時に明示的に有効化できる構成とする。

## Decisions

### 採用: 日付単位の新しい順のローリングバックフィル

- 網羅率を日別状態で測定できる。
- 既存の `RaceResultCollection` と結果取り込みを再利用できる。
- 直近のデータほど予想・検証への効用が高く、途中段階でも価値が出る。
- 月チェックポイントと日ジョブの組み合わせで、再開と部分再試行を両立できる。

### 不採用: 馬の出走履歴だけを過去レース網羅の起点にする

既存馬に関係するレースへ偏り、未登録馬だけが出走したレースを発見できないため、日付単位バックフィルを網羅性の正本とする。ただし、出走予定馬自身の公式情報を正確にする目的では馬起点履歴を自動利用する。履歴レースから別馬の全履歴へ高優先度で再帰展開しない。

### 採用: 今週末出走馬は取得済みでも開催週に再確認する

プロフィールの現在情報と出走履歴は前回取得後に変わり得る。週末予想の精度を優先し、単なる欠損判定ではなく開催週を鮮度境界とする。一方、出馬表の定期更新ごとではなく週1回に抑え、同じ全履歴の過剰な再探索を避ける。

### 採用: 見直し自体を監査可能なジョブにする

長期処理では起動時の計画が数時間後の開催近接度やキュー状態と合わなくなる。見直しを永続ジョブにすることで、常駐・Lambdaの差をなくし、いつ何を見直して優先順位を変えたかを追跡できる。

### 不採用: watchdogへ優先順位見直しを追加する

watchdogは実行基盤の配送・リース健全性を扱う。業務上の取得優先順位まで持たせると、障害修復と計画変更の理由が混ざり、停止・再試行契約も不明瞭になるため分離する。

### 不採用: 起動時に対象期間の全日を一括登録

数年分のジョブと通知が一度に増え、通常収集の遅延、JRA への急激なアクセス、運用画面の見通し低下を招く。小さい上限で継続的に計画する。

### 不採用: 無効化された旧バックフィル Worker をそのまま復活

削除済みの URL 列挙方式へ依存し、現行 JRA ナビゲーションと二重の取得実装になる。旧ジョブ型・設定は移行時の互換確認には使うが、実行経路は現行の日別収集へ統合する。

### 保留: 3年より前への拡張

初回の既定範囲を3年とし、処理時間、失敗率、JRA 公開範囲、分析上の有用性を確認してから別途拡張する。設計上は下限設定の変更で続行できる。

## Acceptance criteria

- 機能が有効な環境では、利用者操作なしに、直近5日範囲より前の JRA 開催日が新しい順で結果収集対象になる。
- 今週末の出馬表で判明した全出走予定馬について、既存データの有無にかかわらず、その開催週にJRA公式プロフィールと全掲載出走履歴が1回ずつ取得対象になる。
- 馬公式情報には出典URL、JRA公開識別子、取得時刻を保持し、同名だけで別馬を更新しない。非公開値を推測せず、取得不能値で既存値を消さない。
- 今週末出走馬の公式プロフィール・履歴探索・不足している直近5走は、当日結果を除く当該馬が関係しない長期バックフィルより先に実行される。直近5走より古い履歴も全掲載分を対象に継続する。
- 同じ馬が複数の今週末レースに登録されても、プロフィール・履歴の有効な自動ジョブは対象開催週につき各1件である。
- 今週末出走馬の履歴はページ送りを含むJRA全掲載分を対象とし、成功済みレースを再試行でやり直さず、失敗・対象外を区別する。
- 当日・直近結果または長期バックフィルで新たに判明した馬も、未取得の公式プロフィール・履歴が各優先度と件数上限に従って補完される。
- 馬履歴から発見したレースを起点に、別馬の全履歴が無制限に高優先度展開されない。
- `AcquisitionPlanReview` が既定15分間隔で永続ジョブとして重複なく登録され、常駐・`--once` / Lambdaの双方で実行できる。
- 見直しのたび、今週末情報の不足、状態別ジョブ件数、最終進捗、チェックポイント、反復失敗、キュー状態を評価し、判断結果と次回予定を確認できる。
- 開催が近づいた場合、未実行の今週末出馬表・出走馬公式情報が長期バックフィルより高い優先度へ更新される。
- 前景ジョブ滞留時は新しい長期バックフィル投入を抑制し、解消後の見直しで設定上限内へ戻る。
- 見直しジョブはRunningジョブを強制中断せず、成功済みチェックポイントを再実行せず、Failed / DeadLetterや全体停止を無条件に解除しない。
- 同じ見直し時間枠の重複実行と、古い見直し世代による新しい判断の上書きが発生しない。
- watchdogによるリース切れ・配送漏れ修復は従来どおり動作し、見直しジョブが同じ再配送を重複して行わない。
- リリース候補構成で見直し間隔を短縮せず15分に設定し、実時間で連続4回以上・合計60分以上の周期確認を行って、登録・実行・次回予定が欠落または重複しない。
- 実時間確認中に、今週末向け不足ジョブの追加、長期バックフィル抑制、前景解消後の再開、変更なしno-opを少なくとも各1回観測する。
- リリース前評価で、見直し実行時間、前景ジョブ待ち時間、キュー深さ、重複数、失敗・DLQ数、JRAページ遷移数、Lambda起動回数・実行時間・メモリ、月間費用見積りを記録する。
- 下記リリース判定をすべて満たし、実測値と評価を本記録へ追記するまで本番有効化しない。
- 初期下限は `InitialResultBackfillYears` で制御され、既定3年の境界日を含む。
- 開催なしの日と日別状態が `Complete` の日は結果収集ジョブを登録しない。
- 通常収集とバックフィルが同じ日を計画しても、有効な日別結果収集ジョブは重複しない。
- 当日・直近収集または利用者起点ジョブが Ready / Running の間、バックフィルの新規登録または次ジョブ実行がそれらを追い越さない。
- 開催中モードで抑制設定が有効な場合、新しいバックフィルを計画しない。
- 1回の計画で登録されるバックフィル開催日数が設定上限を超えない。
- Collector の再起動、同じ計画の再実行、重複通知の後も、完了日と開催なし日を再処理せず保存済み位置から続行する。
- 一部失敗の日は `Incomplete` と成功件数を保持し、上限まで再試行する。上限到達後も他の日のバックフィルは進行する。
- ジョブ詳細または日別状態から、対象日、バックフィル由来、進捗、最終失敗理由を確認できる。
- 常駐モードと `--once` / Lambda モードの双方で、同じ計画・優先順位・冪等性が成立する。
- 既存の直近結果収集、出馬表収集、手動レース再取得、馬起点履歴取得、停止・保留・再開に回帰がない。

6. 再起動、部分失敗、上限到達、Live抑制、重複計画、再帰展開抑止、見直し世代競合、停止中no-opを統合テストする。
7. 検証環境で今週末の代表馬と小さい過去期間から実サイト確認し、プロフィール・全履歴・アクセス量・所要時間を照合する。

## Release readiness evaluation

本番有効化前に、リリース候補のApi・Collector・状態DB・SQS相当の配送を使う隔離検証環境で評価する。見直し間隔は本番予定値の15分から短縮せず、合計60分以上、連続する15分枠を4回以上観測する。単体テストや時計を進める統合テストは事前検証として実施するが、この実時間確認の代替にはしない。

観測シナリオは次を1回の連続セッションに含める。

1. 今週末の出馬表または出走予定馬公式情報を意図的に不足させ、次の見直しで前景ジョブが冪等登録・昇格されることを確認する。
2. 前景ジョブを残した状態で、長期バックフィルの新規投入が抑制されることを確認する。
3. 前景ジョブを正常完了させ、次の見直しで低優先度投入量が設定上限内へ戻ることを確認する。
4. 変更対象がない時間枠で、見直しが成功したno-opとして記録されることを確認する。
5. 同一時間枠の重複トリガーを与え、見直しジョブと副作用が1件に抑止されることを確認する。
6. 実行中の収集ジョブがある状態で見直し、リース・状態・実行が中断されないことを確認する。

### Go / No-Go criteria

次をすべて満たした場合だけGoとする。

- 15分時間枠ごとの見直しジョブが連続4回以上成功し、欠落0件、同一枠の有効重複0件である。
- 各見直しが次の時間枠より前に完了し、見直し自身がキュー滞留原因にならない。
- 今週末向け不足を検出した次の見直し1回以内に、必要な前景ジョブが登録または昇格される。
- 前景滞留中の長期バックフィル新規投入が0件で、前景解消後の次の見直し1回以内に設定上限内で再開する。
- 見直しによるRunningジョブの中断、成功済みチェックポイントの再実行、停止・保留・DeadLetterの自動解除が0件である。
- 見直しジョブ、outbox、SQS相当通知の増加が時間枠あたり各1件以内で、DLQ投入と未処理例外が0件である。
- no-op時間枠でJRAページへ遷移せず、同じ馬・日付への取得が冪等条件を超えて増えない。
- 代表的な今週末収集を含め、個別Lambda相当処理が内部14分期限に収まり、期限超過対象はリリース前に分割または実行ホスト変更対象として明記される。
- 実測したLambda起動回数・実行時間・メモリ、SQS要求数、JRAページ遷移数から月間通常時とバックフィル時の費用・負荷を見積もり、想定運用量として許容可能と記録される。

1項目でも満たさない場合はNo-Goとし、本番フラグを無効のままにする。原因、観測値、修正、再評価結果を `Verification record` に追記し、同じ60分以上の確認をやり直す。実データを変更する検証は隔離環境だけで行い、本番では有効化前の設定・キュー・DLQ・アラームの読み取り確認に限定する。
