## Experience and interaction design

Existing `/settings/horse-id-migration` を段階表示の独立Pageとして拡張。障害/馬診断から移動できる。初見の利用者が次の操作を判断できるよう、各段階のPrimary Actionは一つとし、技術詳細は展開表示する。設計モックは [mocks/recovery.md](mocks/recovery.md)。

1. **保存先を診断**: 明示操作でreadonly診断。保存先、観測時刻、対応状態、不一致の種類、許可された構造情報と次の行動を表示。生SQL、DBパス、業務行、例外全文は表示しない。レポートを安全なJSONとしてコピー可能。未知のSQL構文/識別子は分類とfingerprintに留める。
2. **移行候補を確認**: 既存3件は未選択の参考候補として維持。登録馬を検索/選択し、JRA馬番号10桁を入力して最大16件まで追加できる。旧ID、現登録/初回登録、DOB、source証拠と不足、サーバーで導出した新IDを表示。証拠不足は仮説として明示確認し、同名を自動選択しない。行追加/削除/変更時は古いpreview/確認を破棄する。手入力先は馬番号のみで、任意URL/SQL/新IDは受け付けない。
3. **プレビュー/実行確認**: 共通policy、全設定保存先、対象root/typed references/collision、fingerprintを使用。Unknown/Partial/未確認・未対応があればstage/実行不可。既存のpause状態を確認してから実行。明示確認後にserver GUID依頼を保存し、別の「移行を実行」操作でその固定GUIDのアプリ内実行だけを依頼する。保存だけでは実行しない。
4. **実行と再接続**: 依頼受付/停止待ち/バックアップ/実行中/検証中と、実際の検証済み成功/失敗/Partial/Interruptedを区別。受付成功だけでは移行成功にしない。GUIDをURLへ残す。API停止中の接続断を事前説明し、画面再読込/再ログイン後も同一依頼へ戻る。手動の「状態を更新」で保存された実行状態とjournalを確認し、隠れた自動実行/pollはしない。
5. **復旧**: 移行成功receiptと必要postchecksが揃って初めて既存の障害画面へ誘導。現在の正確な通知IDを確認して再取得を依頼し、pipeline再開は別の明示操作。新taskの成功と3レーンの実進行を確認するまで「復旧完了」にしない。

PCでは完全IDを折返し表示、390pxでは候補/診断情報を縦積み。Fluent componentを優先。Loadingは未取得を0件と表示せず、失敗時は入力/現在状態を保持し、再操作可能な文言を出す。ラベル、inline validation、keyboard/focus、二重送信抑止をbUnit/実browserで検証する。候補追加からプレビューまで画面遷移不要。実行確認後に外部画面の操作を要求しない。
検索エラー時の保持は同じ検索条件の再取得に適用する。条件を変えた場合は以前の検索結果/選択を引き継がず、失敗を0件成功と表示しない。同じ正規化クエリの再取得失敗は入力と前回結果を保持し、古い結果であることを明示して自動選択しない。保存先診断の再取得失敗も前回レポート/時刻を保持する（T4 review closure時の文脈明確化、外部契約変更なし）。

### Durable request and app-owned execution

Stage retry uses a caller idempotency key and immutable request hash mapped to one server GUID in the existing bounded journal. Same key/same contents returns that GUID; different contents is409. The requestKey lookup is journal-only and recovers a lost response. Stage alone never requests execution.

A separate explicit Execute intent records GUID, immutable request, timestamps and phase in the operational journal. The policy/state transitions are pure/testable; adapters handle processes, SQLite/file backup and clock. One explicit intent can be active; a double click, browser reload, API restart or repeated HTTP request cannot create a second physical application. Existing journal64MiB/retention/OS-owner/partial-preservation limits remain. Do not reuse workflow_claimed as a whole-host process lock.

Use a small supervisor mode in the same application/container, with the existing dotnet/DLL ENTRYPOINT unchanged and Docker CMD selecting the supervisor for normal deployment. Explicit existing horse-id-migration GUID arguments override CMD, preserving manual workflow compatibility. The supervisor starts the normal API as an owned child and waits; it is not a new cloud service and has no Docker socket, arbitrary command API or credentials. Private startup modes and fixed child arguments are not request parameters. Local direct API mode may diagnose/preview, but execution is disabled unless supervised lifecycle capability is established.

Execution order is fixed:

1. User explicitly pauses collection using the existing pipeline operation, then confirms Execute. Normal API coordinates only preparation. Recheck persisted pause, wait Running=0 up to10minutes, wait the full900seconds from confirmed pause, then recheck pause/Running. Cancellation, timeout or a changed pause fails closed. No permanent busy loop; bounded per-operation waits, at most1second checks where needed.
2. Normal API stops accepting/finishes requests and hosted services. Supervisor must observe complete API process exit, not merely a pause flag or StopAsync return. Graceful stop has a bound; remaining owned children are terminated/reaped, and inability to establish their exit prevents source writes. Propagate container shutdown safely.
3. All normal API starts and offline writers participate in exclusive runtime leases for the exact configured source set, acquired before business constructors. Combined with a durable maintenance gate, this prevents another instance or a manual CLI from becoming a concurrent writer; failed ownership yields minimal status only. On upgrade, canonical deploy still drains/stops the old container and changes versions safely. Do not infer single-instance protection from the migration journal lock alone.
4. With no business writer, resolve only configured EventStore/Collection/Schedule and optionalLocalQueue; reject aliases/symlinks/nonregular/missing required targets. Make coherent backup of exact configured DBs and present sidecars, check space/capacity/stability/hash manifest and source integrity; preserve existing nonempty-WAL/rollback-journal gates. Use an in-container bounded managed backup adapter, not host-side docker/bash helpers. No arbitrary path input or automatic backup deletion. Backup failure prevents CLI invocation.
5. Invoke only the existing fixed offline command with the saved GUID as a sequential child. Keep its fresh typed preflight/collision/full-preservation and ownership checks. Journal Running/Partial/Interrupted/corrupt states remain fail-closed; never automatically retry a physical application after restart.
6. Keep normal writers excluded until source-set integrity plus required typed/root/reference/projection/sequence/replay postchecks complete. Reuse existing evidence/backup reconstruction where appropriate, but do not treat CLI exit0 or an HTTP200 as complete verification. On success start normal API with collection still paused. Failure exposes authenticated journal-only minimal status, not normal business services. If data application succeeded but verification was interrupted, a separately confirmed request may rerun only readonly verification; it must not reapply data. Unknown or partial writes still need an explicit safe recovery plan, never Reset.
7. After verified migration, exact selected recovery notifications and explicit pipeline resume stay separate; observe replacement success and3lane progress.

During API stop/CLI execution the screen explains temporary loss of connection. Reopening the same URL reads the saved request/operation; it never auto-starts work. Manual status reads are bounded and journal-only, with observed phase/time and safe errors. The new execution-status response also exposes the validated bounded saved manifest and preview fingerprint before execution, so reloaded UI confirms the actual immutable request rather than its default/current inputs; preserve the existing operation-receipt shape and never return owner nonce/paths.
