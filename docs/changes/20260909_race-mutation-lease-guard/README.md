# 収集リース中のレース手動更新を拒否する

- Status: Completed
- Owner: HorseRacingPrediction maintainers
- Created: 2026-09-09
- Updated: 2026-09-09

## Context

収集ジョブがレースをリースして更新している間も、管理画面や通常APIから同じレース情報を更新できる。Collectorの書き込みと手動補正が並行すると、後着した処理が他方の値を上書きし、画面上の成功表示と最終データが一致しない可能性がある。

現行のCollectorと管理画面内 `AdminApiClient` は同じ `X-Api-Key` を利用する。このキーはAPI利用者であることは証明できるが、現在のリースに基づくバッチ処理か、管理画面からの手動操作かを区別できない。任意の自己申告ヘッダーも、実行中リースとの対応を証明しないため排他制御には使えない。

## Goals

- 同一レースを対象とする有効な収集リース中は、通常API・管理画面からのレース情報変更を拒否する。
- 現在の有効なリースを保有するCollectorの書き込みだけを許可する。
- レース単位ジョブと開催日一括ジョブの両方を対象範囲として判定する。
- 拒否時に利用者が理由、対象ジョブ、再試行方法を理解でき、入力値を失わない。
- リース終了・失効・中断後は手動更新を再び許可する。

## Non-goals

- 予想、メモ、馬・騎手・調教師・馬主の編集を同じ排他制御へ含めること。
- 複数Collectorによる同一レースの重複リースを許可すること。
- APIキーを利用者別・サービス別に全面刷新すること。
- 手動更新を待機キューへ自動投入すること。

## Experience and interaction design

レース詳細はリース中も閲覧できる。対象レースに有効な収集リースがある場合、「収集中のためレース情報を編集できません」と状態、リース期限、対象ジョブへのリンクを表示し、編集・インライン補正のPrimary Actionを無効化する。色だけで状態を表現しない。

編集画面を既に開いている場合やAPIを直接呼ぶ場合にも、保存時のサーバー判定を正本とする。409 `RaceCollectionInProgress` を受けたフォームは入力値を保持し、送信ボタン付近とエラーsummaryに「収集完了後に再試行してください」を表示する。リース状態の事前表示は利便性向上であり、排他保証には使用しない。

Collectorの正当な書き込みは既存どおり処理を継続する。リースが期限切れ、中断済み、保留確定、失敗または完了ならロックは解除されたものとして手動更新を許可する。

## Technical impact

### バッチ由来の証明

- Collector実行スコープにJob IDとリーストークンを保持し、データ書き込み用HTTP handlerが `X-Collection-Job-Id` と `X-Collection-Lease-Token` を付与する。
- ヘッダー値をログ、監査理由、例外本文へ出力しない。リーストークンはAPIキーとは別の短命な資格情報として扱う。
- APIはヘッダーの有無だけでバッチ扱いせず、state storeでJob ID、トークン、`Running`、非保留、期限内、対象レースとの一致を検証する。

### 対象レースの判定

- レース単位ジョブはpayloadまたは永続化済み対象情報のRace IDで一致させる。
- `RaceDayReacquisition` はpayloadの対象日と、変更対象レースの開催日が一致する場合に日付内のレースを対象とする。
- 対象を安全に解決できないRunningジョブは無関係な全レースをロックせず、Collector側の当該書き込み資格も不成立として拒否する。

### 適用する変更系API

レースaggregateまたはレース時点データを書き換える経路を共通endpoint filterで保護する。少なくともレース基本情報の作成・補正、出馬表公開、Entry登録・更新、結果宣言、Entry結果、払戻、天候、馬場、オッズ、一括結果登録、再取得refresh保存を含む。再取得ジョブの依頼作成はレースデータ自体を変更しないため対象外とする。

APIは次の順で判定する。

1. 対象レースに有効な収集リースがなければ、従来どおり変更を許可する。
2. 有効な収集リースがあれば、要求のJob ID・リーストークンがそのリースと対象レースに一致する場合だけ許可する。
3. 一致しなければ409 Problem Detailsを返し、`code=RaceCollectionInProgress`、対象Job ID、リース期限を含める。リーストークンは含めない。

ジョブDBとイベントストアが別トランザクションであるため完全な分散ロックとはしないが、書き込み直前に有効性を確認し、Collectorのリース更新により要求処理中の資格を維持する。

## Decisions

### 採用: APIキーではなく有効リースをバッチ資格にする

APIキーはCollectorと管理UIで共有され、現在のジョブ・対象・期限を証明しない。有効リースは既に排他的に発行され、Job ID、対象、期限、状態を持つため、今回の判断に必要な情報を満たす。

### 採用: UI事前表示とサーバー強制を併用する

画面だけの無効化では直接APIや開いたままのフォームを防げない。サーバーの409を排他保証とし、UIは操作前に理由を説明して無駄な入力を減らす。

### 不採用: 自己申告のバッチヘッダー

ヘッダーを知る任意のクライアントがバッチを偽装でき、リース対象外・期限切れでも更新できるため採用しない。

### 不採用: Collector専用の固定APIキーだけで許可する

発信元は区別できるが、現在リースしているジョブ・対象レース・期限を証明できない。資格漏えい時の影響範囲も固定キーの全レースへ広がる。

## Acceptance criteria

1. 対象レースに有効なRunningリースがない場合、既存の手動更新とCollector更新が成功する。
2. 対象レースに有効なRunningリースがある場合、リース資格を持たない変更系APIを409 `RaceCollectionInProgress` で拒否する。
3. 正しいJob ID・リーストークンを持ち、状態・期限・対象が一致するCollector書き込みだけが成功する。
4. ヘッダーだけ、別ジョブのトークン、別レースのトークン、期限切れ、保留・中断・完了済みリースはバッチ資格として拒否する。
5. `RaceDayReacquisition` の有効リースは、その対象日内の全レースだけを保護し、別日を保護しない。
6. レース基本情報、Entry、結果、払戻、天候、馬場、オッズ、一括登録の全変更経路が同じ判定を使用する。
7. リース終了後は手動更新が成功し、古いトークンは使用できない。
8. レース詳細はリース中も閲覧でき、編集操作を理由付きで無効化し、対象ジョブへ移動できる。
9. 保存時409ではフォーム入力を失わず、送信ボタン付近とsummaryに再試行案内を表示する。
10. リーストークンがログ、レスポンス、監査、画面へ出力されない。
11. レース単位再取得、開催日単一ジョブ、収集停止・保留・リース更新に回帰がない。
12. API/Collector/CollectionOperations/component/browserテスト、solution build、`git diff --check` が成功する。

## Delivery plan

1. 対象レースに対する有効リース照会・資格検証をstate storeへ追加する。
2. Collector実行コンテキストとHTTP handlerでJob ID・リーストークンをデータ書き込みへ伝播する。
3. 共通endpoint filterを全レース変更系APIへ適用する。
4. ロック状態照会とレース詳細・編集フォームの説明、無効化、409入力保持を実装する。
5. 異なるジョブ種別、日付一括、期限・状態競合、秘密情報非露出を自動・ブラウザーテストする。
