The counts and timings above were supplied by the operator in the incident handoff. Exact capture timestamps, metric periods, and the underlying AWS or production-console exports are not attached to this record. No temporary recovery action has been performed. In particular, the dispatcher/API has not been restarted, the pipeline has not been paused or resumed, and no task, outbox row, queue message, or failure record has been retried, deleted, or repaired.

## Root-cause boundary and hypotheses

### Supported by repository source and production observations

The leading technical hypothesis is starvation between outbox eligibility/reservation and Lambda execution acquisition:

1. In deployed source `ab1cda45`, `CollectionPlatformStore.GetPendingDispatchesAsync` selects undispatched, available outbox rows whose reservation is absent or expired. It joins their task and resource, but does not require the task to be `Ready` or the outbox generation to equal the task's current dispatch generation.
2. The dispatcher reserves selected rows subject to `MaxInFlightEnvelopes`, sends a wake-only SQS message, and records the queue message ID. The reservation remains live until expiry unless the worker acquires the envelope.
3. `AcquireNextExecutionAsync` rejects an envelope if its task is no longer `Ready` or its generation is stale, returning `NoWork`. The Lambda can therefore acknowledge/delete a wake that made no task progress while its outbox reservation continues consuming the in-flight capacity slot for up to the configured reservation lifetime (reported as 45 seconds in this incident).
4. For wake-only delivery, `MarkWakeSentAsync` records the queue message ID but does not mark the row dispatched. `GetLaneDispatchStateAsync` derives persisted fairness only from rows with `DispatchedAt != null`; therefore these wake reservations do not advance the persisted lane state. The dispatcher advances a local copy only after a successful send, and that local state is discarded at the next polling iteration. Capacity rejection also leaves the selected lane unchanged during the current loop. Thus stale reservations can consume capacity without durable lane progression.
5. With limited `MaxInFlightEnvelopes`, repeatedly selecting stale/ineligible rows can consume dispatch capacity while leaving eligible tasks undispatched. The observed continuing SQS traffic and zero queue depth are consistent with wake delivery and acknowledgement, not proof of collector crashes.

Current `main` retains the same eligibility gap in `GetPendingDispatchesAsync`. An earlier draft incorrectly said the v2 endpoint returns HTTP 204 on `NoWork`. The store method returns a non-nullable `CollectionExecutionAcquireResult` on every branch, including `NoWork`; the endpoint's `lease is null`/204 branch is therefore unreachable, and current behavior serializes the result as HTTP 201 JSON. The worker's JSON parsing is consistent with this implementation. This is non-causal implementation/spec drift because the route ledger expects 204; the proposed resolution is to standardize on 201 JSON and add endpoint-to-client/ledger end-to-end coverage, but do not treat this as a production or CI blocker. The actual current-main cutover risk is the deployment workflow's use of v1 admin paths after deploying the v2 route surface, described under C3 and T4. The failed `verify` step is separate and its cause is unknown.

### Not yet proven

The live database has not been inspected at outbox-row level. It is not yet established that stale or ineligible outbox rows are prevalent enough in production to explain the full 3,718-task backlog. A narrowly scoped, read-only SQLite aggregate is needed to count, without returning identifiers, undispatched rows by task status, generation match, reservation expiry, and lane, alongside eligible Ready/current-generation rows. Until that observation exists, stale-outbox starvation remains a strongly supported mechanism and the leading root-cause hypothesis, not a fully proven production prevalence claim.

The 17 actionable findings may contain isolated deterministic failures. They should not be bulk retried and are not presumed to account for the broad backlog.

## Goals

- Establish whether stale/ineligible outbox reservations are consuming dispatch capacity in production without exposing task, race, resource, or credential identifiers.
- Restore meaningful dispatch progress through the narrowest evidence-backed and reversible action.
- Correct the dispatcher eligibility and reservation handling so a `NoWork` acquisition cannot strand a `MaxInFlightEnvelopes` slot for the reservation timeout.
- Make lane fairness and dispatch/acquisition outcomes observable and alertable.
- Ensure API and Lambda contracts are verified and deployed as a coordinated pair.

## Non-goals

- Bulk deletion, bulk retry, or blanket regeneration of queued work.
- Clearing the SQS queue or DLQ to make depth metrics look healthy.
- Restarting, pausing, resuming, or repairing production before the current state is captured and the relevant action is authorized.
- Treating a successful Lambda invocation or empty queue as evidence of collection progress.
- Deploying current `main` before the v2 client contract and workflow route verification failures are resolved.

## Proposed permanent-response design

This is the concrete design selected for review. It does not authorize code changes, schema migration, production access, or deployment. The incident hypothesis remains provisional until T1's read-only aggregate is reviewed.

### Eligibility and consistency rules

The candidate query joins `collection_task_outbox`, its task, resource, and current repair-hold state. A candidate is dispatchable only when all predicates hold at selection and again at reservation:

- The pipeline is not paused; the task status is `Ready`; both task and outbox `AvailableAt` are due; and the dispatcher aggregation-delay rule has elapsed.
- Outbox `DispatchedAt` is null and the row is unreserved or its reservation deadline has expired.
- `outbox.DispatchGeneration == task.DispatchGeneration`.
- The resource is not covered by an active race-repair hold, using the same canonical identity matching as existing hold checks.
- Exactly one undispatched outbox row exists for that task's current generation. A count of zero or greater than one is an integrity anomaly, not a candidate.

The query returns a bounded keyset page ordered by due time and outbox key, not an unbounded materialized list. If a selected candidate becomes invalid before reservation, that rejection consumes scan work only, not `MaxInFlightEnvelopes`; the same dispatch cycle continues with the next candidate/page up to a configured scan budget. The scan cursor advances past rejected entries so an invalid first row cannot repeat forever and block valid work. A later poll resumes from a persisted cursor/fairness state.

`Ready` task with no current-generation undispatched outbox: do not synthesize an outbox row, change task status, retry, or delete anything. Increment the missing-outbox aggregate/metric, log a bounded reason, alert, and leave the task for a separately reviewed repair path.

Multiple current-generation undispatched outbox rows for a task: exclude all those rows from dispatch, count and alert on the cardinality anomaly, and preserve every row. Do not choose one, merge, or silently delete a duplicate. Old-generation rows are also preserved but are never dispatch candidates.

### State machine and invariants

| State/transition | Guard and atomic effect | Failure behavior |
| --- | --- | --- |
| Eligible → Reserved | In one SQLite `BEGIN IMMEDIATE` transaction, re-read every selected task/outbox/resource/hold row; recheck due, `Ready`, current generation, unique current outbox, unreserved/expired, not held, pipeline active, and capacity. Assign a fresh `ReservationToken`, `EnvelopeId`, `WakeId`, and expiry; update persisted lane cursor in that transaction. | On any changed predicate, reserve nothing for that candidate, emit a bounded rejection reason, and continue the bounded scan. Transaction/DB error performs no partial reservation and records a cycle error. |
| Reserved → WakeSent | Send one opaque wake for the reserved envelope; after SQS confirms success, persist the queue receipt and sent outcome using the same reservation token. | Definite SQS rejection may conditionally release that exact current-generation reservation. Ambiguous timeout or failure to persist the receipt leaves the reservation untouched until expiry; a late wake is fenced by token/expiry and is idempotently acknowledged. |
| WakeSent → Acquired | Worker POSTs the wake. In one transaction, validate the wake identity, envelope, token, active expiry, undispatched rows, task Ready/current generation/due, no hold, unique cardinality, and no conflicting lease; create the execution lease, mark the envelope rows dispatched, and clear active reservation fields (`ReservationToken`, deadline, and `WakeId`). | An active existing lease is never released. A matching unexpired `StartPending` acquisition can return the same lease idempotently; a duplicate for a Running/terminal lease returns typed `NoWork`. |
| Reserved/WakeSent → NoWork | Return HTTP 201 JSON with `Status=NoWork`, a bounded reason enum, and release outcome. Conditional release requires exact wake/envelope/token, undispatched rows, reservation still active, outbox generation still equal to the task generation, and no active execution lease. The update only clears that exact reservation; it never mutates task state or another token. | If the predicate matches zero rows, generation changed, cardinality is ambiguous, or a lease exists, do not release; return a typed no-op outcome. Stale, duplicate, or expired wake messages are acknowledged. DB/transport failure does not run compensating SQL; current queue behavior acknowledges the wake and the durable scanner/expiry path recovers it. |
| Reservation expiry → Reeligible or Preserved anomaly | Expiry reclaimer makes only eligible, unique, current-generation rows available for a fresh token; stale generations, missing rows, duplicates, and active holds remain unchanged and capacity-neutral. | Never clear or regenerate an anomalous row automatically. Surface its metric/alert and preserve evidence for a separately reviewed repair. |

**Invariants:** (1) only a current `Ready`, due, unheld, unique outbox row can reserve capacity; (2) reservation validation, capacity accounting, and lane-cursor advancement share a write transaction; (3) one reservation identity can create at most one execution lease; (4) a NoWork release is token-scoped and cannot release an active worker lease; (5) acknowledgements are idempotent because the DB outbox/lease state, not the SQS message, is the durable source of work; (6) no path bulk-deletes, retries, or repairs rows.

**Wake identity and persisted fairness:** add nullable `WakeId` to outbox reservations and add a singleton `collection_dispatcher_fairness_state` record containing the last granted lane, last non-Realtime lane, Realtime burst count, monotone reservation sequence, keyset scan continuation `(AvailableAt, OutboxId)`, and update time. Version-19 migration is additive. Generate the wake ID before reservation and store it with the token/envelope in the same transaction; an old row with no WakeId cannot satisfy a new release predicate and is left to expire/re-dispatch. Persist lane state at reservation grant so it survives dispatcher/API process restart, rather than deriving fairness only from `DispatchedAt` (wake-only delivery intentionally leaves that null). When the bounded page scan ends, persist the last examined key and continue there on the next poll; wrap to the beginning after reaching the end so newly eligible earlier keys are eventually considered. Cursor advancement on an invalid candidate is durable but consumes no in-flight capacity.

Lane policy preserves the existing allocator contract: when all lanes have eligible work, dispatch at most four consecutive Realtime envelopes, then give the next non-Realtime turn to Normal and Background in alternation; after that turn Realtime may resume. Without Realtime, alternate Normal and Background. Under continuously eligible work, each lane therefore gets a turn within at most ten successful reservation grants. The reservation cursor advances on a durable reservation even if send later fails, preventing retries or restarts from pinning the same lane; send failures remain visible and their reservations recover by exact release only when delivery is definitely rejected, otherwise by expiry.

### Acquire reason and release categories

`CollectionExecutionAcquireResult` remains a non-nullable HTTP 201 JSON result for both statuses. Add a bounded `Reason` enum for `Acquired`/`NoWork`; at minimum cover `InvalidWake`, `PipelinePaused`, `DuplicateOrAlreadyLeased`, `ReservationMissingOrExpired`, `ReservationIdentityMismatch`, `OutboxCardinalityMismatch`, `TaskNotReady`, `GenerationMismatch`, `TaskNotDue`, `RepairHoldActive`, and `NoDispatchableRows`. Include a bounded release outcome: `NotAttempted`, `Released`, `AlreadyReleasedOrChanged`, `SkippedStaleGeneration`, `SkippedActiveLease`, or `SkippedAmbiguousRows`. An internal database failure remains a 5xx/transport failure, not a fabricated NoWork. The Lambda acknowledges typed stale/duplicate/expired NoWork; an API/DB failure also does not mutate the task and is recovered by the existing durable scanner after reservation expiry.

### Failure and concurrency boundaries

- Two dispatchers racing for the same row serialize at `BEGIN IMMEDIATE`; the first commits one token/envelope, the second re-reads and skips it. Capacity is counted by distinct active execution leases plus distinct *currently eligible* reserved envelopes, not by stale/held/terminal/generation-mismatched reservations.
- If status/generation/hold changes between page selection and reservation, transaction-time validation rejects the candidate. If it changes after reservation and before acquire, acquire returns the specific NoWork reason; release may clear only the exact still-current reservation. A stale-generation reservation is capacity-neutral and remains stored until ordinary expiry.
- Duplicate delivery of the same wake is idempotent. An active StartPending lease can be returned only for the identical wake/envelope/token; otherwise the existing lease is retained and the duplicate is acknowledged as NoWork. An expired reservation cannot create a lease after a replacement token is committed.
- A process crash after reservation but before send leaves a bounded reservation until expiry; no work row changes. A crash after SQS accepted the wake but before receipt persistence may still allow that wake to acquire; if it does not, scanner retry follows expiry. A crash after acquire commit but before HTTP response leaves the lease as the single owner; duplicate wakes cannot start a second execution.
- For a queue send that is definitively rejected, release only the exact token after checking current generation and no lease. For timeout/ambiguous acceptance, do not release or immediately send another wake; keep the token until acquisition or expiry. If a send succeeded but `MarkWakeSent` failed, retain token/row and rely on the wake or expiry. A failure affecting one envelope must not prevent bounded scanning of later independent candidates.
- Partial/ambiguous API responses follow the same rule: typed NoWork is acknowledged; transient acquire transport failure is acknowledged without a task mutation and scanner/expiry recovers; a DB error cannot release anything. Keep the pipeline's existing pause/safety controls and do not weaken deterministic failure handling.

### Observability contract

Use structured logs and CloudWatch namespace `HorseRacingPrediction/CollectionDispatch`; never emit IDs, URLs, message bodies, tokens, or raw exceptions as metric dimensions. A maximum of 16 configured definition labels is emitted; unlisted definitions use `OTHER`.

- Counters: `dispatch_cycle_total{outcome}` (`NoCandidates`, `Reserved`, `CapacityFull`, `CandidateRejected`, `ReserveConflict`, `WakeSent`, `WakeSendDefiniteFailure`, `WakeSendAmbiguousFailure`, `WakeReceiptPersistFailure`); `acquire_total{status,reason}`; `reservation_release_total{outcome}`; `execution_lease_reclaimed_total{reason}`.
- Gauges: eligible Ready rows and oldest eligible age by lane/definition; due Ready tasks missing a current-generation outbox; current active/expired eligible reservations; in-flight execution leases; cardinality-anomaly task counts.
- Throughput: wake sent, acquire success, and terminal task completion counts by lane/definition and five-minute window, with dimensions bounded as above.
- Alerts: (a) any Ready-missing-outbox or duplicate-current-outbox count remains nonzero for five minutes; (b) a lane/definition has eligible Ready rows but no successful acquire/completion for `max(5 minutes, 3 × dispatch interval)`; (c) at least five NoWork results in five minutes while eligible reservation count is at capacity and successful acquire is zero; (d) reservation release or SQS send failures exceed five in five minutes. Thresholds are configurable and checked in tests; initial values are reviewed against the T1 baseline before T5.

## Test and delivery plan

### Required regression matrix

| Case | Expected invariant/result |
| --- | --- |
| Old/stale outbox generation; task terminal/not Ready | Candidate query excludes it; reserve recheck rejects if state changes; no capacity consumed; NoWork reason is bounded. |
| Task status or generation rotates between selection and reserve | Immediate transaction rejects it and continues to the next bounded candidate; no stale token is committed. |
| Two API dispatcher processes reserve the same candidate concurrently | Exactly one token/wake wins; active capacity is not exceeded; losing dispatcher continues its scan. |
| Duplicate SQS delivery / same wake retried | At most one execution lease; exact StartPending retry is idempotent; duplicate running/terminal wake returns NoWork and is acknowledged. |
| Reservation expires before a delayed wake arrives | Old token cannot acquire or release replacement token; old wake is acknowledged; scanner issues a new token. |
| Active repair hold exists or appears between select and reserve/acquire | Candidate is excluded or transaction rejects it; exact reservation release only when identity/generation/no-lease predicates match; hold itself is untouched. |
| Ready task without current-generation outbox | Count/metric/alert is emitted; task and existing rows are preserved; no synthetic outbox, retry, or delete. |
| More than one current-generation undispatched outbox for a task | Entire task is skipped and anomaly counted; no arbitrary winner, merge, or deletion. |
| `MaxInFlightEnvelopes=1`, continuous Realtime + Normal + Background load | Persisted 4-Realtime / alternating non-Realtime turns; each lane gets a turn within ten successful reservation grants; same result after API restart and send failure. |
| Process restart after grant, before send, after send-before-receipt, and after acquire-before-response | Reservation expiry or exact wake can recover; lane cursor persists; never create a second active lease or lose task/outbox rows. |
| Reservation token/wake/envelope mismatch on NoWork release | No row is cleared; `Skipped...` outcome returned; another worker's lease remains intact. |
| Active or expired execution lease | Active lease cannot be released by NoWork; expired lease is reclaimed transactionally and only then may valid current work be redelivered. |
| Queue send definite rejection, ambiguous timeout, and partial multi-envelope cycle | Definite rejection releases exact safe token; ambiguous outcome retains token until expiry; successful sibling envelope stays sent; remaining eligible candidates continue on a later/current bounded scan. |
| Pipeline paused during candidate/reservation/acquire | No new reservations/acquires; typed NoWork is acknowledged; resume does not erase anomaly or task history. |
